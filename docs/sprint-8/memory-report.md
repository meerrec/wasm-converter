# Память модели DOCX и пик разбора (бюджеты ROADMAP §9)

Отчёт волны 3 спринта 8. Закрывает числами бюджеты памяти DOCX из ROADMAP §9
и плана спринта: **≤ 256 Б на абзац, ≤ 128 Б на run, ≤ 192 Б на ячейку** и
**пиковая память ≤ 200 МиБ на 50 МБ DOCX с изображениями**. Замеры сделаны
слайсами волн 1–2; здесь они сведены и перепроверены.

Дата перепроверки: 09.10.2026, ветка `sprint/8-docx-parse-fuzz`, HEAD
`fb8cd0b` + незакоммиченные правки параллельных слайсов (в дереве шли fuzz и
сборки агентов — на память это влияет слабо, на время заметно).

## Команды, которыми сняты числа

```bash
cargo test -p doc-converter-docx --test memory -- --nocapture          # размеры узлов и таблицы по фикстурам
cargo build --release -p doc-converter-docx --example mem_probe        # адресно: см. «ловушку» ниже
/usr/bin/time -l target/release/examples/mem_probe --open-only target/fixtures/docx-large/memory_50mib.docx
bash scripts/check-docx-memory.sh target/release/examples/mem_probe target/fixtures/docx-large/memory_50mib.docx 200
```

Пик RSS снимает системный `time(1)` (`maximum resident set size`; на Linux
GNU `-v` — килобайты, на macOS BSD `-l` — байты; оба разобраны в гейте), в
таблицах МиБ = Б / 2²⁰. Разбор идёт в том же процессе, поэтому чтение файла
и `open` целиком входят в пик.

## Бюджеты размера узлов

| Узел | Бюджет ROADMAP §9 | Факт | Запас |
| --- | ---: | ---: | ---: |
| `Paragraph` | 256 Б | **88 Б** | 2,9× |
| `Run` | 128 Б | **64 Б** | 2,0× |
| `Cell` | 192 Б | **128 Б** | 1,5× |

Источник — `crates/docx/tests/memory.rs`, тесты `paragraph_stays_within_budget`,
`run_stays_within_budget`, `cell_stays_within_budget`: печатают
`size_of::<T>()` и падают при выходе за бюджет. Проверено 09.10.2026: 88 / 64 /
128 Б — тесты зелёные.

### Что для этого сделано: пять полей — за указателем

| Тип | Было | Стало | Убрано за указатель | Коммит |
| --- | ---: | ---: | --- | --- |
| `Paragraph` (`model/inline.rs:23,27,38`) | 2072 Б | 88 Б | `ppr` (1280) + `mark_rpr` (272) + `section_break` (456) | `d38db99` |
| `Run` (`model/inline.rs:90`) | 328 Б | 64 Б | `rpr` (272) | `21d98fc` |
| `Cell` (`model/table.rs:78`) | 312 Б | 128 Б | `borders` (192) | `e61374b` |

Значения «было» согласуются с измеренными размерами: замена указателя (8 Б)
на значение даёт 88 − 24 + 2008 = 2072, 64 − 8 + 272 = 328 и
128 − 8 + 192 = 312; 2072 Б названо прямо в сообщении `d38db99`. Форма
enum'ов и JSON-контракт при этом не менялись: `Box` для serde прозрачен,
`Model → JSON → Model` остаётся lossless, round-trip-тесты не трогались.

## Замер по фикстурам

`prints_memory_table_for_fixtures` (`crates/docx/tests/memory.rs`) обходит
весь корпус коммитируемых фикстур обходчиком `crates/docx/tests/common/stats.rs`.

Итог по корпусу: **97 фикстур, разобрано 94** (три фатальные по замыслу —
`broken/macro_enabled.docx`, `broken/no_document_xml.docx`,
`broken/truncated_zip.docx`, ADR-0016); абзацев 300, run 437, ячеек 127,
таблиц 16, рисунков 13, `Unknown` 30; **Σ `size_of` 2 550 136 Б**,
**оценка heap 2 262 736 Б**.

Что именно считают эти две колонки:

- **`Σ size_of`** — сумма `size_of::<T>()` по слотам, лежащим в куче по
  значению: элементы `Vec`, значения `Box` (у `Box<RawPPr>` считается размер
  самого `RawPPr`, а не 8 байт указателя), значения `BTreeMap`. Слот считается
  **один раз — по типу варианта**: `Inline` в `Vec<Inline>` — это 424 Б, и
  `Run` внутри варианта отдельно не считается, его байты уже в слоте; иначе
  корпус посчитался бы дважды.
- **`heap`** — оценка динамической памяти: `String::capacity()` и
  `Vec::capacity() × size_of::<T>()`, у `StyleId` — длина строки. Это именно
  оценка: накладные расходы аллокатора (заголовок блока, округление до класса
  размера), выравнивание и внутренние коллекции `RawPPr`/`RawRPr` (`tabs`,
  `unknown`) не учтены, а `capacity` бывает заметно больше длины. Годится для
  сравнения фикстур и ловли регрессий порядка, а не как абсолютная величина.

Таблица **по категориям** (17 строк) — целиком; таблица по 97 фикстурам

## Находка: таблица стилей весит больше тела

| Часть документа | Σ size_of, Б | Доля |
| --- | ---: | ---: |
| styles | **1 220 800** | 47,9 % |
| body | 1 157 624 | 45,4 % |
| остальное (footnotes, comments, headers, footers, numbering, rest) | 171 712 | 6,7 % |

В теле те же свойства лежат за указателями, а в стилях — по значению:
`ParagraphStyle` весит 1704 Б (1552 из них — `ppr` + `rpr`), `TableStyle`
2072, `NumberingStyle` 1656, `DocDefaults` 1552. Стилей в корпусе немного,
но каждый дороже абзаца в 20 раз; на 94 фикстурах это половина памяти модели.
Бюджета на стили нет, в этом спринте ничего не менялось — это первый задел
Спринта 9: бокинг (или общий пул) свойств стиля даст больше, чем любые правки
тела.

## Пиковая память процесса

### Гейт DoD 6: `memory_50mib.docx` — выполнен

| Метрика | Значение |
| --- | ---: |
| Вход | 59 951 803 Б = 57,17 МиБ (6000 абзацев, 75 PNG 512×512, без таблиц) |
| Пик RSS | **156,78 МиБ** (164 397 056 Б) |
| Бюджет | 200 МиБ |
| Запас | **≈ 43 МиБ = 21,6 % бюджета** |
| Разбор | 31,0 мс в прогоне гейта (в записях слайса — 25–30 мс) |

Прогон гейта закончился строкой `DoD: пик RSS 156.78 МиБ на memory_50mib.docx
(вход 57.17 МиБ, 6000 абз., 75 изобр.); предел 200 МиБ` и кодом 0.
Вес здесь набирают изображения (75 шумовых PNG по ~770 КиБ), а не текст, —
ровно та формулировка бюджета, по которой гейт и назван.

### Плотный профиль: зафиксированное отклонение

Второй профиль ROADMAP §9 — `profile_50mib.docx` (100 000 абзацев тела +
12 000 абзацев ячеек, 500 таблиц, 50 PNG 448×448; подробности — в
[`bench-profile.md`](bench-profile.md)). Пики RSS, `/usr/bin/time -l`, по три
прогона на фикстуру (разброс ≤ 0,1 МиБ):

| Фикстура | Вход, МиБ | Абзацев | Пик RSS, МиБ |
| --- | ---: | ---: | ---: |
| `profile_50mib.docx` | 55,51 | 112 000 | **874,6** |
| `many_paragraphs.docx` | 12,09 | 100 000 | 652,5 |
| `wide_table.docx` | 12,65 | 40 000 | 377,1 |
| `mixed.docx` | 11,78 | 51 015 | 369,2 |
| `numbered_list.docx` | 11,28 | 50 000 | 355,7 |
| `many_images.docx` | 14,73 | 200 | 33,4 |

**Уточнение к записи в CI.** В шапке джобы `perf-docx` плотный профиль
записан как ≈650 МиБ, и это число локально воспроизводится — но на
`many_paragraphs.docx` (684 163 072 / 684 179 456 / 684 130 304 Б в трёх
прогонах, 652,5 МиБ). Прямой замер самого `profile_50mib.docx` на этой машине
даёт **874,6 МиБ** (917 143 552 / 917 209 088 / 917 225 472 Б), на треть
больше: у профиля 350 знаков текста на абзац против 170 и на 12 % больше
абзацев, к тому же CI-число снято на Linux-раннере с другим аллокатором.
Информационный шаг CI печатает именно профиль, поэтому при следующей правке
шапки число стоит либо перемерить на раннере, либо подписать явно, что ≈650 —
это `many_paragraphs`.

**Из чего складывается пик** (для профиля; часть — прямые замеры, часть —
оценка снизу по измеренным `size_of` и счётчикам `mem_probe`):

- вход 55,5 МиБ — `mem_probe` читает файл целиком, как и вызывающий `open`;
- **копия входа внутри `parse_docx`** — ещё 55,5 МиБ (`bytes.to_vec()`, см.
  «Известный запас»);
- распакованный `word/document.xml` — 42,15 МиБ;
- модель: только свойства — `ppr` 112 000 × 1280 Б = 137 МиБ, `mark_rpr`
  112 000 × 272 Б = 29 МиБ, `rpr` 112 050 × 272 Б = 29 МиБ; слоты `Paragraph`
  9,4 МиБ и `Run` 6,8 МиБ — итого ≈ 211 МиБ снизу, плюс текст (~36 МиБ) и
  ёмкости векторов;
- промежуточные аллокации разбора (стек открытых элементов, временные
  `Vec`/`String`, удвоение при росте коллекций).

Точная разбивка потребовала бы инструментации аллокатора — её в срезе нет;
но порядок виден и без неё: пик задаёт модель **на узел**, а не байты входа.
Опорное число: между `numbered_list` (50 000 абзацев, 355,7 МиБ) и
`many_paragraphs` (100 000, 652,5 МиБ) — ≈ **6,1 КиБ пика RSS на абзац**, на
два порядка больше `size_of::<Paragraph>()` = 88 Б. Пустой `Box`-`ppr`
выделяется каждому абзацу (`document.rs:672`), поэтому 200 МиБ на плотном
профиле **недостижимы без потокового разбора**, который в спринт не входит.

**Почему гейт стоит на `memory_50mib`, а профиль идёт информационной строкой.**
Бюджет сформулирован как «пиковая память на 50 МБ DOCX **с изображениями**»
(ROADMAP.md:776, план спринта): нагрузка — медиа, текст вторичен. На профиле
нагрузку задают абзацы, и красный шаг там был бы ложной тревогой; поэтому в
`perf-docx` профиль печатается шагом «profile 50 MiB (info)» без порога, а
`memory_50mib` проходит через `scripts/check-docx-memory.sh` с жёстким
пределом 200 МиБ.

## Известный запас: копия входа в `parse_docx`

`crates/docx/src/parse.rs:736` — `Archive::open_with_limits(bytes.to_vec(),
limits)`: вход копируется целиком. Для `memory_50mib` это ≈ 57 МиБ сверх
модели, для профиля — 55,5 МиБ (заметная доля пика в 156,8 и 874,6 МиБ
соответственно). API не меняется: на `&[u8]` опираются fuzz-цели и политика
ADR-0016; но это известный резерв — передача владения или `Cow` сняла бы один
полный размер входа с пика, не трогая разбор.

## Операционная ловушка: у двух примеров одно имя

У `crates/pdf/examples/mem_probe.rs` и `crates/docx/examples/mem_probe.rs`
совпадает имя, и cargo пишет оба в `target/release/examples/mem_probe`
(предупреждение «output filename collision»; в каталоге при этом лежат оба
хешированных бинарника — DOCX ≈ 0,77 МБ, PDF ≈ 2,9 МБ, — а некэшированное имя
`mem_probe` достаётся собранному последним). Последствия и лечение:

- в CI пример собирается **адресно**: `cargo build --release -p
  doc-converter-docx --example mem_probe` — сборка `--workspace --examples`
  или любой таргет PDF-крейта подменила бы бинарник под тем же именем, и
  гейт памяти падал бы на чужом числе;
- локально сборка PDF-примера ломает DOCX-гейт, пока DOCX-пример не
  пересобран; быстрая проверка, чей бинарь лежит под именем, — вывод
  `mem_probe --open-only <файл>`: DOCX-пример печатает «вход … МиБ, абзацев
  …», PDF-пример просит `.xlsx` (`usage: mem_probe <fixture.xlsx | путь>`).

## Как воспроизвести

```bash
pnpm gen:docx-fixtures:large          # ≈ 11 с, пишет target/fixtures/docx-large (в git их нет)

cargo test -p doc-converter-docx --test memory -- --nocapture

cargo build --release -p doc-converter-docx --example mem_probe
/usr/bin/time -l target/release/examples/mem_probe --open-only target/fixtures/docx-large/memory_50mib.docx
/usr/bin/time -l target/release/examples/mem_probe --open-only target/fixtures/docx-large/profile_50mib.docx
bash scripts/check-docx-memory.sh target/release/examples/mem_probe target/fixtures/docx-large/memory_50mib.docx 200
```

Первая строка — генерация фикстур, вторая — числа модели, третья–пятая —
сборка примера и пики RSS, последняя — тот же гейт, что в CI (`perf-docx`,
шаг «DoD 6 memory gate»). Генератор
детерминирован (фиксированные таймстампы и порядок записей ZIP), поэтому
числа воспроизводимы на тех же фикстурах.

## Вывод

- Бюджеты размера узлов выполнены с запасом 1,5–2,9×: 88 / 64 / 128 Б при
  256 / 128 / 192. Держится он пятью `Box`; форма модели и JSON-контракт не
  менялись.
- DoD 6 выполнен: пик на `memory_50mib` — **156,78 МиБ** при бюджете 200 МиБ,
  запас 43 МиБ (21,6 %).
- Плотный профиль — **зафиксированное отклонение**: 874,6 МиБ, в 4,4 раза
  выше бюджета; причина — модель на узел (≈6,1 КиБ пика на абзац), а не
  размер файла. Лечится потоковым разбором, который в спринт 8 не входит.
- Память модели малых документов на 48 % состоит из таблицы стилей — самый
  крупный задел под Спринт 9.
