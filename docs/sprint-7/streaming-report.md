# B3: пик памяти PDF-экспорта после постраничной записи

Задача B2b-3 (Спринт 7). Проверяет числами два критерия DoD 8 из
[ADR-0010](../adr/0010-printpdf-fork.md) и гипотезу «пик ≈9 МиБ при любом
числе страниц» из [спайка B1](../analysis/pdf-streaming-spike.md) §6.

Дата замера: 06.10.2026. Ветка `sprint/7-pagination-pdf`.

## Протокол

- **Машина:** Apple M3 Pro, 18 ГиБ RAM, macOS 26.6.1 (сборка 25G76), arm64.
  Замер нативный, не wasm.
- **Сборка:** rustc 1.98.0; `cargo build --release -p doc-converter-pdf
  --example mem_probe`; профиль release — `lto = "fat"`,
  `codegen-units = 1`, `opt-level = "s"`, `panic = "abort"`
  (`Cargo.toml`, `[profile.release]`).
- **Состояние дерева:** HEAD `d6af8d4` + незакоммиченные правки параллельных
  сессий. Пик снимал бинарь `target/release/examples/mem_probe` со sha256
  `c5a17510…df2cebb48`; он собран из состояния с комбинированным sha256
  (`crates/pdf/src`, `crates/xlsx/src`, `crates/render/src`, `crates/core/src`,
  `vendor/printpdf/src`, по `*.rs`) `09a0a2e5…3b99c07e` — проверено: на момент
  сборки свежее бинаря не было ни одного .rs. После сборки дерево двигалось
  дальше (параллельная сессия правила `chart.rs`) — на эти фикстуры это не
  влияет: диаграмм в книгах нет, путь `chart.rs` не исполняется.
- **Метрика:** пик RSS всего процесса — `/usr/bin/time -l`, строка
  `maximum resident set size` (байты; в таблицах МиБ = байты / 2²⁰). Разбор
  книги входит в число: он идёт в том же процессе.
- **Экспорт:** `PdfExporter::new(PdfOptions::default())` (`compress = true`),
  лист 0. Sink-путь — `export_xlsx_sheet_to` в `CountingSink` (байты
  считаются, не хранятся); полный путь — `export_xlsx_sheet` (PDF целиком в
  `Vec<u8>`), как его видит вызывающий.
- **Прогоны:** два прохода подряд по девяти конфигурациям (3 фикстуры × 3
  режима), плюс четыре прогона каждой конфигурации ранее — на бинаре до правок
  `background.rs`/`chart.rs` (см. «Стабильность»).
- Все команды — из корня репозитория.

Генерация временных фикстур:

```bash

node target/tmp/gen-pages.mjs 4792 100 target/fixtures/scale-100-pages.xlsx
```

```js
// target/tmp/gen-pages.mjs
import ExcelJS from 'exceljs';

const rows = Number(process.argv[2]);
const pages = Number(process.argv[3]);
const out = process.argv[4];
if (!rows || !out) {
  console.error('usage: node target/tmp/gen-pages.mjs <rows> <pages> <out.xlsx>');
  process.exit(2);
}

const wb = new ExcelJS.Workbook();
wb.creator = 'doc-converter fixtures';
wb.created = new Date(Date.UTC(2026, 0, 1));
wb.modified = new Date(Date.UTC(2026, 0, 1));
const ws = wb.addWorksheet(`${pages} страниц`);
ws.getColumn(1).width = 10;
ws.getColumn(2).width = 32;
for (let r = 1; r <= rows; r += 1) {
  ws.getCell(r, 1).value = r;
  ws.getCell(r, 2).value = `Позиция ${r}: строка отчёта`;
}
await wb.xlsx.writeFile(out);
console.log(`${out}: ${rows} строк`);
```

Замечание о воспроизводимости: скрипт-зеркало — не часть репозитория, поэтому
на свежем клоне его нужно создать по тексту выше; 500-страничная фикстура
воспроизводится штатно — `node scripts/gen-fixtures.ts` (он перегенерирует и
остальные фикстуры с эталоном).

## Критерии

### Относительный (DoD 8): sink-путь, пик на 500 ≤ 1,5 × пика на 50 — НЕ ВЫПОЛНЕН

**25,40 / 10,03 = 2,53×** (2,50–2,62× по всем девяти прогонам). Разбор:

1. **Книга сама по себе даёт 2,20×.** `--open-only`: 7,38 МиБ на 50 страницах
   против 16,22 на 480. Это не экспорт и не стриминг: разобранная модель xlsx
   линейна по строкам (≈450 Б на строку). Даже экспорт с нулевой памятью
   оставил бы пик ≥ 16,22, то есть **критерий в формулировке «пик RSS всего
   процесса» на этой фикстуре недостижим**: потолок 16,22/7,38 = 2,20 > 1,5.
   Ожидание ADR-0010 «постоянная часть ≈8,3 МиБ (процесс, книга, шрифты)» —
   верно только для маленькой книги: 8,3 МиБ — это уровень 13-страничной
   фикстуры Спринта 6.
2. **Рабочий набор экспорта тоже растёт: 2,65 → 9,18 МиБ** (3,5×), ≈15,6 КиБ
   на страницу. Это **не** писатель PDF: `StreamSession` на страницу хранит
   только её id и запись xref (десятки байт), содержимое уходит в `Write`
   сразу (`write_page` → `write_indirect`,
   `vendor/printpdf/src/streaming.rs`). Растёт **пагинация**: `paginate()`
   строит `Vec<SheetPage>` со всеми `PaintedCell` заранее, и он живёт весь
   экспорт (`painter.rs` — и пре-проход шрифтов, и цикл записи идут по нему
   целиком). `PaintedCell` (`crates/pdf/src/pagination.rs:83`) — ссылка на
   ячейку + `RectPx` + `CellStyle` (копия стиля), то есть на каждую из 46 000
   ячеек заводится запись ≈166 Б. Оценка: ≈7,3 МиБ на 480 страницах — почти
   весь прирост остатка.
3. Если сделать пагинацию ленивой (страница собирается, пишется,
   освобождается), sink-отношение стало бы ≈ (16,2 + 2,6…3) / 10,0 ≈ 1,9–2,0 —
   всё ещё выше 1,5 из-за пункта 1. Чтобы уложиться в 1,5, менять надо не
   только PDF-путь: либо ленивый разбор книги (xlsx-крейт, вне B2), либо
   другую метрику критерия (например, наклон на страницу или рабочий набор
   экспорта вместо полного RSS).

### Абсолютный: полный путь на 500 ≤ 40 МиБ — ВЫПОЛНЕН

**28,21 МиБ** — запас 11,79 МиБ (29% бюджета). Ориентир ADR-0010 «сегодня
≈228 МиБ» → улучшение ≈8,1×. Оговорка в сторону ужесточения: в это число
входит служебный re-parse lopdf внутри `mem_probe` (подсчёт страниц); по
разнице «полный − sink» на 480 страницах он стоит ≈2,8 МиБ, то есть без него
пик был бы ещё ниже.

### DoD 1 (500 страниц < 3 с) — не под угрозой

480 страниц экспортируются за 159–173 мс — запас больше 17×. Стоимость
двойной отрисовки пре-прохода глифов, по замеру в комментарии `painter.rs`
(та же конфигурация), — ≈7% (35 мс из 162 мс); выбор «двойная отрисовка»
подтверждается: и по времени, и по памяти пре-проход держит одну страницу за
раз. Итог: механизм пре-прохода не меняется.

## Вывод

- Стриминг записи **сработал**: множитель страницы у PDF-документа убран —
  старый путь копил ≈450 КиБ на страницу, новый sink растёт на ≈37 КиБ на
  страницу. Полный путь на
  480 страницах — 28,2 МиБ против ≈228 МиБ по базе ADR-0010.
- Абсолютный критерий (≤40 МиБ) выполнен с запасом 29%.
- Относительный критерий (≤1,5×) **не выполнен — 2,53×**, и на нынешней
  фикстуре не может быть выполнен одним PDF-слоем: 2,20× даёт разбор книги.
  Остаток сверх книги (0,33×) — пагинация, материализуемая целиком.
- Комментарий `export_xlsx_sheet_to` («память экспорта не растёт с числом
  страниц») точен для писателя, но не для суммы: рабочий набор экспорта растёт
  на ≈15,6 КиБ на страницу из-за пагинации — формулировку стоит уточнить в
  том срезе, который будет её трогать.
- Решение по критерию (оставить как есть / переопределить метрику / завести
  срез на ленивую пагинацию) — за оркестратором; этот отчёт даёт числа и
  разбор, а не меняет DoD.

## Сомнения и ограничения

- Замер нативный; в браузере (wasm32) числа иные — их снимет Playwright
  (B6). Аллокатор wasm32 страницы ОС не возвращает, но и профиль там другой.
- Отнесение остатка к пагинации — по замерам трёх режимов и чтению кода, а не
  по пофазовой инструментации: `mem_probe` её не умеет, а правка `painter.rs`
  вне среза B2b-3. Оценка в ≈166 Б на ячейку сходится с размером
  `PaintedCell`, но это косвенная улика.
- Фикстура — две колонки без картинок, диаграмм и комментариев; эти ветки
  добавляют свою память и в этот замер не входят (отдельные срезы Спринта 7).
- Одна машина, один профиль (`opt-level = "s"`); на `opt-level = 3` числа
  могут слегка сдвинуться.
