# Политика хранения и обновления визуального baseline

**Версия политики:** `0.1.0-draft.1`  
**Состояние:** `draft`; хранилище, лимиты и approvers имеют статус `proposed`  
**Задача:** [#79](https://github.com/meerrec/wasm-converter/issues/79)  
**Связанные документы:** [`certification-matrix.md`](certification-matrix.md), [`manifest.schema.json`](manifest.schema.json)

Наличие исходной фикстуры, SHA-256 или снимка экрана не делает его принятым baseline. Эталоном становится только неизменяемый набор, связанный с версией матрицы, проверенным manifest, средой Office Online и явным решением reviewer. Обычные build/test команды не имеют права создавать, заменять или удалять reference PNG.

## 1. Предлагаемая модель хранения

| Решение | Предложение | Состояние |
|---|---|---|
| Метаданные | Один `manifest.json` на документ в `test-fixtures/strict-viewer/<format>/<fixture-id>/`; схема и corpus index версионируются в Git | `proposed` |
| PNG | Git LFS, отдельный path-scoped набор `test-fixtures/strict-viewer/**/reference/*.png`; никаких PNG в этом документальном PR | `proposed` |
| PDF от Word Online | Сохранять рядом через Git LFS, потому что он связывает экспорт Office с rasterized PNG и позволяет проверить повторную растеризацию | `proposed` |
| Предел одного PNG | 4 МиБ; превышение требует проверки размера страницы и отдельного решения, а не JPEG или уменьшения DPR | `proposed` |
| Предел первого корпуса | 250 МиБ суммарно для PNG и PDF; фактический размер публикуется в PR #75 | `proposed` |
| Retention | Принятые baseline не перезаписываются. Старые baseline сохраняются, пока на них ссылается release или активная ветка расследования | `proposed` |
| Доступ CI | `git lfs pull` с явным include только для strict-viewer; после получения артефактов capture/diff работает без Office и внешней сети | `proposed` |

Git LFS не считается выбранным до решения `accept-storage`. При отказе от LFS допустимо заменить только storage adapter на immutable release assets или object store с content-addressed URL. Схема `corpus.storage` уже отделяет вид хранилища от состояния захвата. Нельзя добавлять ссылку на изменяемый `latest`, личный диск, временный CI artifact или Office URL как единственное хранилище baseline.

Локальные пути не входят в переносимый manifest. `image.uri` разрешается относительно `corpus.storage.rootUri`; захватчик и comparator не должны угадывать каталог по имени файла. SHA-256 обязателен и для исходного документа, и для каждого PNG, и для сохранённого PDF.

## 2. Идентичность baseline

Предлагаемый `baselineId` формируется как:

```text
strict-viewer-<corpus-version>-<matrix-version>-<environment-id>-<short-digest>
```

`short-digest` вычисляется от канонического corpus index, содержащего отсортированные записи `source.path`, `source.sha256`, `capture.id`, `image.sha256` и все параметры среды. Алгоритм канонизации и длина digest должны быть зафиксированы реализацией #75 до первого принятого baseline. До этого нельзя сравнивать baseline только по человекочитаемой версии.

Один baseline связывается с:

- полным SHA-256 каждого DOCX/XLSX;
- версией certification matrix и схемы manifest;
- полным набором capture ID и SHA-256 изображений;
- Office application/build при доступности;
- OS, browser, viewport, DPR, zoom, locale, timezone и font assets;
- PDF SHA-256 и версией `pdftoppm` для `docx.pdf`;
- Git commit, в котором принят manifest и corpus index.

Версия собственного движка не является частью reference identity. Она обязательно записывается в actual run и `report.json`, чтобы сравнение можно было отнести к конкретной ревизии. Изменение движка само по себе не создаёт новый reference baseline.

## 3. Первичный захват #75

1. Начать после решений `accept-modes`, `accept-environment`, `accept-dynamic` и `accept-storage`.
2. Сверить кандидатов с [`certification-matrix.md`](certification-matrix.md). Сохранить шесть обязательных регрессионных фикстур. Отсутствующие обязательные фикстуры добавить или изменить статус возможности явным решением.
3. Проверить SHA-256 входных документов и запретить изменение DOCX/XLSX между захватом и принятием.
4. Подготовить версионированную шрифтовую среду. Не полагаться на незаписанные системные шрифты.
5. Открыть документ в Word Online или Excel Online только на машине подготовки baseline. Не встраивать Office в продукт, тестовый runtime или comparator.
6. Установить состояние из manifest: режим, лист, страницу, диапазон, scroll, zoom, DPR, comments/revisions и hidden sheets. Отключить UI Office вне области сравнения.
7. Дождаться открытия документа, загрузки шрифтов и стабильного изображения по наблюдаемому состоянию. Не использовать длинный фиксированный sleep как доказательство готовности.
8. Сохранить PNG напрямую. Для DOCX PDF сохранить исходный PDF и выполнить `pdftoppm -png -r 144`; промежуточный JPEG запрещён.
9. Заполнить manifest по схеме. Добавить маски только по правилам матрицы, с прямоугольником, причиной и независимым текстовым правилом.
10. Повторить захват в чистой сессии той же среды. До принятия baseline reference обязан быть стабилен; расхождение двух reference capture классифицируется как проблема среды или документа, а не маскируется.
11. Провести независимый повторный захват вторым исполнителем по документу без устных допущений. Совпадение capture IDs, размеров, содержимого и SHA-256 либо объяснённая разница фиксируется в PR.

Полный набор содержит 20 DOCX и 20 XLSX. Для DOCX сохраняются все страницы каждого выбранного документа. Для XLSX отдельно перечисляются Normal view captures и все печатные страницы каждого выбранного Print Preview листа. Ограничение набора страниц возможно только явным решением с причиной; оно не позволяет заявить полную сертификацию документа.

## 4. Обязательные проверки manifest

JSON Schema проверяет форму, но принятие требует дополнительных семантических проверок:

- `source.path` существует, остаётся внутри `test-fixtures/`, размер и SHA-256 совпадают;
- `source.format`, `reference.application`, `view.format` и capture kinds согласованы;
- `schemaVersion` поддерживается потребителем, `matrixVersion` соответствует принятой матрице;
- capture ID и mask ID уникальны внутри manifest;
- DOCX page numbers непрерывны от 1, пропусков и дублей нет, число captures равно числу страниц reference;
- XLSX sheet index/name существует, лист видим, captures соответствуют выбранному режиму;
- Normal view имеет видимый диапазон, scroll и active cell; Print Preview имеет полный набор печатных страниц выбранного листа;
- каждый URI существует, PNG имеет валидную сигнатуру и заявленный RGB8 или RGBA8, фактические размеры и SHA-256 совпадают с manifest; comparator декодирует оба варианта в RGBA;
- каждая маска находится внутри изображения, имеет причину и текстовое правило; маски не покрывают всё изображение и не перекрывают обязательную проверку содержимого;
- для `docx.pdf` присутствуют `exportedPdf` и `environment.rasterizer`;
- среда совпадает со значениями, принятыми для baseline; незаписанный font fallback отсутствует;
- суммарный размер и размер каждого артефакта укладываются в принятые лимиты;
- в capture/diff runtime нет Office URL, сетевого вызова или зависимости от учётных данных Office.

Эти проверки должны стать быстрым отдельным gate до дорогого capture. Сам документальный PR не заявляет, что такой validator уже реализован.

## 5. Явное принятие и обновление

Обновление baseline всегда выполняется отдельным PR, не смешанным с изменением rendering engine, comparator thresholds или certification matrix. Если причина обновления одновременно требует изменения кода, сначала принимается код со старым baseline и отчётом расхождений, затем открывается baseline-only PR.

Baseline-only PR обязан содержать:

1. прежний и новый `baselineId`;
2. причину каждого изменения и ссылку на issue;
3. список добавленных, удалённых и изменённых captures;
4. reference-before/reference-after/diff для каждого изменённого изображения;
5. новые manifest и доказательство успешной schema/semantic validation;
6. полную среду и сведения о повторном захвате;
7. подтверждение, что DOCX/XLSX не изменились, либо отдельное обоснование новой фикстуры;
8. полный offline report собственного вьюера против предлагаемого baseline;
9. фактический суммарный размер хранилища;
10. явные approvals maintainer и независимого reviewer захвата.

Предлагаются два approvals: один maintainer и один QA/reviewer, не выполнявший захват. Это требование остаётся `proposed` до решения `accept-baseline`. Команда принятия может упаковать и проверить кандидата, но не может поставить accepted status, изменить stable corpus pointer или завершить PR без review.

Запрещены:

- `--update-snapshots` или аналог в обычном test/CI;
- копирование `actual/` в `reference/` в задаче исправления движка;
- автоматическая маска по найденным отличиям;
- повышение цветового допуска ради зелёного результата;
- удаление страницы, листа или документа из corpus ради устранения failure;
- перезапись существующего content-addressed artifact;
- принятие baseline по одному среднему SSIM или выборочным страницам.

## 6. Offline comparison и коды выхода

После получения baseline capture и diff не обращаются к Office. Comparator читает только immutable reference, actual и явно разрешённые маски. Каждый capture получает отдельный результат, а ошибка одной фикстуры не скрывает остальные.

| Предлагаемый код | Условие | Значение |
|---:|---|---|
| 0 | Все обязательные captures имеют `match` | Успешная сертификация выбранного прогона |
| 1 | Есть `visual-diff` или `page-mismatch` | Измеренное несоответствие, harness исправен |
| 2 | Есть `missing-reference` или `capture-error`, но нет кода 3 | Неполный или неуспешный захват, нельзя выдавать за визуальное расхождение |
| 3 | Есть `harness-error`, schema error, corrupt artifact или несовместимая версия | Сломан контур, результаты не сертифицируют движок |

`match` относится к одному capture и возможен только при успешных структурных проверках. Общий успех требует покрытия всего обязательного набора. `report.json` содержит engine revision, baselineId, matrix/schema versions, статус каждого capture, пути reference/actual/diff и диагностику. `report.html` показывает те же изображения и сортирует худшие результаты, не меняя машинный статус.

## 7. Откат и аудит

Откат выполняется новым явным PR, который возвращает ссылку на ранее принятый immutable baseline. Старые PNG и PDF не удаляются в том же PR. Откат reference не откатывает код движка автоматически.

Для каждого accepted baseline сохраняются corpus index, manifest, hashes, approvals, capture notes и итоговый offline report. Если артефакт недоступен или его hash не совпадает, результат `harness-error`; нельзя скачать замену из Office или принять ближайший по имени файл.

## 8. Граница текущего документального PR

Этот PR создаёт только контракт, JSON Schema и политику. Он не добавляет reference PNG, не выбирает окончательные 40 документов, не реализует capture/diff/validator и не меняет публичный API. После решений maintainer документы переводятся в accepted отдельным коммитом, а #75 получает окончательный corpus index и инструкцию хранения.
