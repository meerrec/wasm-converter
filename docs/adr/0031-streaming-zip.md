# ADR-0031: Потоковый ZIP и `ReadableStream`-вход

**Статус:** Принято
**Дата:** 21.10.2026
**Контекст:** `docs/architecture.md`, Фаза 2 — потоковый парсинг; критическое
замечание №2 (OOM и zip bomb)
**Связанные ADR:** [ADR-0015](0015-ooxml-zip-limits.md) (лимиты ZIP),
[ADR-0030](0030-format-plugin-traits.md) (trait-слой),
[ADR-0032](0032-cancellation.md) (отмена, планируется)

---

## Контекст

- Сейчас файл целиком лежит в памяти main-потока (`ArrayBuffer`) и целиком
  копируется в воркер и в wasm-память (`xlsx_open`/`docx_open` берут
  `Vec<u8>`). Для 55-МиБ документа это три полных копии на пике.
- Central directory ZIP лежит в конце архива: разобрать пакет раньше прихода
  последнего чанка невозможно по формату. Поэтому «потоковый парсинг» — это
  не ранний рендер, а три других выигрыша: (1) main-поток держит не файл, а
  один чанк; (2) прогресс загрузки; (3) загрузку можно отменить до парса.
- Лимиты ADR-0015 (`ZipLimits`) уже стоят и остаются: zip bomb ловится ими,
  а не потоковостью.

## Решение

1. **Вход `ReadableStream<Uint8Array>` дополнителен к `ArrayBuffer`.** Оба
   пути ведут к одному парсу: `ArrayBuffer` — как сейчас, стрим — чанками в
   воркер.
2. **Парс стартует после конца архива** (`end-stream`, EOCD получен).
   Распределение выигрыша фиксируется числами: пик памяти main-потока для
   файла в 55 МиБ падает с полного размера до размера одного чанка;
   воркер по-прежнему держит байты документа (их просят PDF- и текстовый
   экспорт), но собирает их чанками, а не разовым трансфером.
3. **Бюджеты §9 не меняются** (DOCX ≤ 200 МиБ, PDF ≤ 40 МиБ). Для
   stream-пути добавляется регрессия «пик ≤ путь-через-буфер + 32 МиБ» —
   страховка от двойной материализации чанков.
4. **`async_trait` не вводится.** Чанки копятся в буфере воркера,
   `end-stream` вызывает синхронный парс (`FormatPlugin::parse`, ADR-0030).
5. **`SegmentedBuffer`** — внутренний тип `crates/core`
   (`Read + Seek` над списком чанков), не публичный trait: `Read`/`Seek`
   реализованы на самом типе (передача по ссылке получается бланкетно).
   `zip::ZipArchive<R: Read + Seek>` работает поверх него без переписывания
   библиотеки. `Archive` переходит на `ZipArchive<Box<dyn Read + Seek>>`:
   `Archive::new(Vec<u8>)` и `Archive::from_segmented(SegmentedBuffer)`
   сводятся к общему `open<R: Read + Seek + 'static>(reader)`. `from_segmented`
   принимает буфер по значению: парс одноразовый, а заимствование
   потребовало бы lifetime в `Archive` и во всех его потребителях.
6. **Реестр потоков — в каждом wasm-модуле свой.** Байты между wasm-инстансами
   (viewer и ленивый docx-модуль) не передаются без копии через JS, поэтому
   `stream_new/append/free` живут и в `crates/wasm` (для XLSX), и в
   `crates/docx-wasm` (для DOCX). Воркер копит чанки на JS-стороне и шлёт в
   wasm **один append всего буфера** в `end-stream`, когда модуль формата
   точно загружен: поштучные аппенды гонялись бы с асинхронной загрузкой
   модуля (сообщения воркера обрабатываются асинхронно), а единый append
   убирает гонку и оставляет копию в wasm только на время парса —
   `xlsx::open_segmented` / `docx::parse_docx_segmented` →
   `Archive::from_segmented`. Копия на границе JS→wasm неизбежна без SAB и
   принимается.
7. **Протокол** — три новых InMsg: `open-stream { id, format, totalSize? }`,
   `append { id, bytes }` (transfer), `end-stream { id, aborted? }`. Ответ —
   обычные `opened`/`docx-opened` либо `WorkerErrorMsg { code: 'open' }`.
   Воркер держит `Map<id, { format, streamId, target, chunks, received,
   moduleReady }>`: запись появляется синхронно (append/end-stream не должны
   обгонять await загрузки DOCX-модуля). При известном `totalSize`
   `sourceBytes` предвыделяется и заполняется по месту — второй копии на
   сборку нет, пик памяти воркера равен пути через буфер; без размера чанки
   собираются в конце (плюс одна копия на время сборки).
8. **Публичный API:** `open(source: ArrayBuffer | ReadableStream<Uint8Array>,
   opts?: { size? })` в обоих вьюерах; `onProgress?: (loaded, total?) => void`
   в `XlsxViewerOptions`/`DocxViewerOptions`. Main читает стрим циклом
   `reader.read()`, шлёт чанки по 1 МиБ, `reader.cancel` помечает
   `end-stream { aborted: true }`, пустой поток (0 байт) воркер отвергает сам —
   оба случая отвечают `WorkerErrorMsg { code: 'open' }` с сообщением
   «stream aborted». Заявленный размер сверяется с фактом: лишние байты —
   ошибка «stream exceeds declared size», недокачанный поток — «stream
   aborted».

## Последствия

- `Archive::new` и лимиты не меняются — существующие парсеры и тесты не
  затронуты.
- `ReadableStream` в старых браузерах может отсутствовать: путь
  `ArrayBuffer` остаётся дефолтным, стрим — опциональная возможность
  вызывающего.
- Отмена загрузки (до `end-stream`) — бесплатно: чанки просто не
  доезжают; отмена парса/раскладки — ADR-0032.
