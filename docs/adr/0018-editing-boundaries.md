# ADR-0018: Границы редактирования в v1

**Статус:** Принято
**Дата:** 05.10.2026
**Контекст:** архитектурное ревью v2, обсуждение предложения «нормализованная модель на клиенте через Jotai для будущей интеграции с онлайн-редактированием»
**Связанные ADR:** ADR-0003, ADR-0004, ADR-0005, ADR-0013, ADR-0019

---

## Контекст

На этапе планирования Спринтов 8–10 поступило предложение: держать нормализованную документную модель на стороне клиента (main thread), используя менеджер состояния (Jotai) — с прицелом на будущую интеграцию с онлайн-редактированием и коллаборацией.

Предложение затрагивает три уже принятых архитектурных решения:

1. **§3.3 роадмапа** — «Main не рендерит и не парсит — только DOM, ввод, UI».
2. **ADR-0003** — граница `crates/render`: документная модель формата (`xlsx::model`, `docx::model`) живёт в Rust; на main — только view state.
3. **§2 роадмапа (Скоуп)** — редактирование, коллаборация и real-time синхронизация явно отнесены к non-goals v1.

При этом проект находится в состоянии, когда Спринт 8 (парсинг DOCX) ещё не начат, а продукт v1.0 заявлен как **просмотрщик и конвертер**, а не редактор. Модель документа в Rust/WASM в воркере — не деталь реализации, а несущая конструкция: на ней стоят zero-copy через Transferables, отсутствие дублирования состояния, единая логика метрик текста для canvas и PDF (ADR-0005).

Предложение фактически требует пересмотра этих решений до того, как продукт подтвердил потребность в редактировании.

---

## Решение

### 1. v1 — read-only, без исключений

Документная модель живёт **только** в Rust/WASM в воркере. На main-потоке она не дублируется, не зеркалируется и не сериализуется в JS-структуры.

Данные передаются между воркером и main только через:

- RPC (`WorkerRequest` / `WorkerResponse`);
- `DisplayList` (готовые команды отрисовки);
- `Transferable` (`ArrayBuffer`, `ImageBitmap`, PDF-байты);
- SAB — как ускорение, не как обязательное условие (ADR-0004).

### 2. Jotai — только для view state

Менеджер состояния на main (Jotai, Zustand, что угодно) используется **исключительно** для:

- текущий лист / страница;
- скролл, зум, DPR;
- выделение, hover, активная ячейка;
- тема (`light` / `dark`);
- состояние UI (открыт ли диалог, идёт ли экспорт);
- ошибки уровня UI.

**Не используется** для:

- абзацев, runs, ячеек, стилей, нумерации;
- дерева документа;
- истории изменений;
- чего-либо, что является источником истины для рендера.

### 3. `NodeId` — вводится, но без editing-инфраструктуры

Со Спринта 8 в модель вводится `NodeId(u64)` — монотонный счётчик при парсинге, уникальный в пределах одного открытия документа (см. ADR-0019).

Формат: `struct NodeId(u64)`. Не UUID. Не глобально уникальный. Не переживает переоткрытие документа.

Зачем:

- snapshot-тесты `insta` становятся стабильнее;
- hit-test возвращает ID узла, а не индекс в `Vec` (важно при вложенных таблицах и floats);
- отладка: `tracing` логирует `NodeId`, а не «абзац №47 в третьей таблице»;
- задел под будущий editing без обязательств.

Чего `NodeId` **не** даёт и не должен давать в v1:

- command-паттерн;
- undo/redo;
- diff/patch;
- сериализацию для синхронизации;
- стабильность между сессиями.

### 4. Что явно НЕ делается в v1

- Command API (`Command::InsertParagraph`, `Command::FormatRun`).
- Undo/redo, история изменений.
- Diff/patch, merge, разрешение конфликтов.
- Yjs, Automerge, CRDT-слои любого вида.
- Offline-режим и синхронизация.
- Awareness (курсоры других пользователей).
- Сериализация модели для передачи между клиентами.
- Персистентные структуры данных (персистентные `Vec`, HAMT, copy-on-write на горячем пути).

### 5. Что делается как «не закрывать дверь»

Дешёвые решения, совместимые с read-only v1 и не мешающие будущему редактированию:

- **Чистые парсеры:** `bytes → Model`, без глобального состояния.
- **`serde::Serialize` / `Deserialize` на модели** — не для редактирования, а для `insta`, отладки и benchmark-фикстур. Почти бесплатно.
- **`NodeId` на узлах** — см. §3.
- **Иммутабельность на уровне API:** парсер возвращает `Document`, дальше модель не мутируется до Спринта 9. Мутации внутри Rust-крейта — норма.
- **Разделение слоёв:** `model` → `layout` → `DisplayList` → `painter`. Это уже есть в ADR-0003, и это же — естественная точка входа для будущего editing-слоя.

## Последствия

### Положительные

1. **Спринты 8–10 не удорожаются.** Модель остаётся компактной: 48 байт на ячейку XLSX, 256 на абзац DOCX. Без command-паттерна, undo/redo и сериализации для diff.
2. **ADR-0003 не пересматривается.** Граница `render` сохраняется, DOCX layout в Спринте 9 не потребует переписывания.
3. **Нет дублирования состояния.** Rust-модель — единственный источник истины. Нет расхождений между Rust и JS-зеркалом.
4. **Производительность сохраняется.** Zero-copy через Transferables, никакой сериализации модели в JS на горячем пути.
5. **Продукт фокусируется на том, что заявлено в §2.** Просмотрщик и конвертер, не редактор.
6. **`NodeId` даёт пользу сразу** — snapshot-тесты, hit-test, отладка — не дожидаясь editing.

### Отрицательные

1. **Если редактирование станет основным сценарием, потребуется новый ADR и, вероятно, частичный пересмотр модели.** Это осознанный риск: платить сейчас за гипотезу дороже, чем переделать потом.
2. **Отсутствие command-паттерна означает, что будущий editing-слой будет не «встроен», а «построен поверх».** Парсеры не изменятся, но модель получит обёртку.
3. **`NodeId` без стабильности между сессиями** — не подходит для сохранения документа. Если когда-нибудь понадобится, будет отдельное решение.

### Нейтральные

1. **Jotai (или другой менеджер состояния) остаётся допустимым** — для view state. Это не архитектурное решение, а деталь UI.
2. **`serde` на модели** — добавляет немного кода, но окупается сразу.

## Альтернативы

### A. Нормализованная модель на main через Jotai (отклонено)

**Суть:** зеркалировать документную модель в JS-структурах на main, редактировать через Jotai-атомы, синхронизировать с Rust.

**Почему отклонено:**

- Две модели, которые разойдутся. Классика жанра.
- Jotai не спроектирован для графов на 100k узлов. Атомы на каждый абзац — это тысячи подписок, каждая перерисовка — O(подписчиков).
- Jotai работает в React. Воркер — не React. Значит, синхронизация между Rust-моделью и Jotai-моделью потребует отдельного слоя, тестов и отладки.
- Преждевременно: продукт не редактор.

### B. Command-паттерн в Rust уже в v1 (отклонено)

**Суть:** спроектировать модель так, чтобы все изменения шли через `Command`, с заделом на undo/redo и diff.

**Почему отклонено:**

- Удваивает объём парсеров, модели, тестов.
- Удорожает Спринт 8 с 2 недель до 4–6.
- Не даёт ничего для v1: read-only сценарий не требует команд.
- Command API появится, когда появится editing, и будет отдельным слоем, не затрагивающим парсеры.

### C. Yjs на main как источник истины (отклонено)

**Суть:** `Y.Doc` на main, Rust — функция `YjsDoc → DisplayList`.

**Почему отклонено:**

- Материализация Yjs в Rust на каждый рендер — дорого.
- `RawPPr` / `RawRPr` (ADR-0013) не выживают в Yjs-структурах без потерь.
- Rust перестаёт быть источником истины. Модель DOCX становится одноразовой.
- Offline-first и awareness — задачи продукта-редактора, не просмотрщика.

### D. Модель на main без состояния, только сериализация (отклонено)

**Суть:** Rust сериализует модель в JSON, main держит её как обычный JS-объект, рендерит через UI-фреймворк.

**Почему отклонено:**

- JSON-модель на 100k узлов — десятки мегабайт и секунды на парсинг.
- Теряется zero-copy.
- Рендер через DOM/React не даёт 60 FPS на больших документах.
- Противоречит всей архитектуре §3: OffscreenCanvas в воркере, painter в Rust.

## Триггер для пересмотра

ADR пересматривается, если выполняется **хотя бы одно**:

1. Продукт требует онлайн-редактирования как **основного** сценария (не «когда-нибудь»).
2. Появляется требование коллаборации в реальном времени.
3. Появляется требование offline-режима с последующей синхронизацией.
4. Появляется требование сохранять документ в промежуточном формате с историей.

При срабатывании триггера — новый ADR (ADR-00XX), в котором выбирается между:

- **Вариант A (Rust — источник истины, `yrs` в воркере):** сохраняет текущую архитектуру, Rust остаётся источником истины, Yjs — транспорт. Offline и awareness сложнее.
- **Вариант B (Yjs на main — источник истины, Rust — рендерер):** даёт экосистему Yjs, offline-first, awareness. Rust-модель становится одноразовой, сериализация на каждый рендер.

Решение принимается **на момент срабатывания триггера**, не сейчас.
