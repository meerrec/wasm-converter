# ADR-0020: Границы парсера и writer

**Статус:** Принято
**Дата:** 05.10.2026
**Контекст:** обсуждение «парсер как сериализатор/десериализатор» перед Спринтом 8
**Связанные ADR:** ADR-0018, ADR-0019

---

## Контекст

Слово «сериализация» в контексте парсера DOCX обозначает три разные вещи, которые часто смешивают:

1. **Парсер** — `bytes (DOCX) → Model`. Это десериализация.
2. **`serde` в JSON** — `Model ↔ JSON`. Формат для тестов, отладки, benchmarks.
3. **Writer** — `Model → bytes (DOCX)`. Это запись DOCX.

Если не зафиксировать границу, кто-то в команде решит, что «раз парсер есть, давайте сделаем writer, это же симметрично». Это **не** симметрично.

---

## Решение

### 1. Парсер = десериализатор

```rust
pub fn parse_docx(bytes: &[u8], limits: ZipLimits) -> Result<Document, ParseError>;
```

- Чистая функция `bytes → Model`.
- Без побочных эффектов.
- Детерминирован (один вход → одна модель).
- Присваивает `NodeId` в порядке обхода (ADR-0019).
- Не имеет обратной функции `Model → bytes`.

### 2. `serde::Serialize` / `Deserialize` на модели — да

- `Model → JSON → Model` lossless.
- Используется для:
  - snapshot-тестов `insta`;
  - отладки (dump модели в файл);
  - benchmark-фикстур (быстрая загрузка);
  - differential-тестов (сравнение моделей).
- Не для DOCX.
- Property-тест на 100 фикстурах.

Это **дёшево** и **полезно сразу**. `#[derive(Serialize, Deserialize)]` на модели — почти бесплатно. Включается в Спринт 8.

### 3. Writer в DOCX — нет

`Model → bytes (DOCX)` **не реализуется** в v1.

Причины:

- Это editing (ADR-0018).
- Round-trip `DOCX → Model → DOCX` не бывает lossless: теряются `rsid`, `proofErr`, неизвестные элементы, порядок атрибутов, namespace-префиксы. Word при открытии такого файла может показать предупреждение.
- Для просмотрщика и конвертера writer не нужен.

Если когда-нибудь понадобится — это отдельный крейт `crates/docx-writer`, отдельный ADR, отдельный спринт.

### 4. Что это значит для Спринта 8

Модель должна:

- ✅ реализовывать `serde::Serialize` и `Deserialize`;
- ✅ проходить round-trip `Model → JSON → Model` без потерь;
- ❌ не реализовывать `to_docx_bytes()`.

Парсер должен:

- ✅ быть чистой функцией `bytes → Model`;
- ✅ быть детерминированным (один вход — одна модель);
- ✅ присваивать `NodeId` в порядке обхода;
- ❌ не иметь обратной функции `Model → bytes`.

Это даёт:

- snapshot-тесты работают;
- differential-тесты работают (сравнение через JSON);
- отладка работает;
- будущий writer не блокируется, но и не проектируется сейчас.

### 5. Асимметрия парсера и writer

| Парсер | Writer |
|---|---|
| Читает любой валидный DOCX | Пишет только тот DOCX, который сами сгенерировали |
| Lossy: игнорирует неизвестное | Lossless: не может игнорировать |
| Тестируется на 100 фикстурах | Тестируется на round-trip с Word (тяжело) |
| Нужен в v1 | Не нужен в v1 |
| Чистая функция `bytes → Model` | Чистая функция `Model → bytes` |

Writer — это **отдельный продукт**, не «обратная функция парсера». Причины:

1. **Парсер lossy by design.** Он игнорирует `w:rsid`, `w:proofErr`, `w:lastRenderedPageBreak`, неизвестные элементы. Writer не может их игнорировать, если хочет, чтобы Word открыл файл без предупреждений.
2. **Парсер читает любой валидный DOCX.** Writer пишет только тот DOCX, который сами сгенерировали из модели. Это разные контракты.
3. **Парсер тестируется на 100 фикстурах.** Writer тестируется на round-trip `DOCX → Model → DOCX → Word`, что требует Word в CI. Это отдельный уровень сложности.
4. **Парсер нужен в v1.** Writer — нет. Продукт — просмотрщик и конвертер, не редактор.

### 6. Что НЕ значит это решение

- **Не значит**, что модель нельзя менять. Внутри Rust-крейта мутации — норма (парсер строит модель пошагово).
- **Не значит**, что нельзя делать экспорт в другие форматы. PDF, PNG, Markdown, HTML, CSV — это отдельные exporter'ы, не writer в DOCX.
- **Не значит**, что writer никогда не появится. Он появится, когда продукт потребует сохранения DOCX, и это будет отдельный ADR.

### 7. Триггер пересмотра

ADR пересматривается, если:

1. Продукт требует сохранения DOCX.
2. Продукт требует конвертации между форматами OOXML (DOCX → DOCM, DOCX → DOTX и т.п.).
3. Продукт требует редактирования с сохранением.

При срабатывании — новый ADR, новый крейт `crates/docx-writer`, отдельный спринт. Решение о формате (round-trip lossless vs lossy write) принимается там же.

## Последствия

### Положительные

1. **Ясность.** Парсер — не writer. Команда не путает три разные сущности.
2. **Snapshot-тесты работают.** `serde` на модели даёт JSON для `insta`.
3. **Differential-тесты через JSON.** Сравнение моделей — это сравнение JSON, дёшево и стабильно.
4. **Будущий writer не блокируется.** Модель спроектирована так, что writer можно добавить позже.
5. **Меньше кода в Спринте 8.** Writer — это недели работы, которые не нужны сейчас.

### Отрицательные

1. **Пользователь не может сохранить DOCX.** Это non-goal v1, документируется в README.
2. **Round-trip DOCX невозможен.** Если пользователь откроет и «сохранит» документ, содержимое изменится.
3. **Writer потребует отдельного ADR и спринта.** Это будущая работа, не текущая.

### Нейтральные

1. **`serde` на модели** — добавляет немного кода, но окупается сразу.
2. **`NodeId` не сериализуется в DOCX** — при записи (если появится) ID нужно регенерировать.

## Альтернативы

### A. Writer в v1

**Суть:** реализовать `to_docx_bytes()` вместе с парсером.

**Почему отклонено:**

- Non-goal v1 (ADR-0018).
- Дорого: 4–6 недель работы.
- Тестировать тяжело: нужен Word в CI для round-trip.
- Не даёт ничего для просмотрщика и конвертера.

### B. Без `serde` на модели

**Суть:** snapshot-тесты и differential-тесты через собственный формат.

**Почему отклонено:**

- `serde` — стандарт, дёшево, работает с `insta`.
- Собственный формат — ещё один слой кода.
- JSON удобен для отладки и diff.

### C. Только `Serialize`, без `Deserialize`

**Суть:** модель можно дампить в JSON, но нельзя загрузить обратно.

**Почему отклонено:**

- Round-trip test невозможен без `Deserialize`.
- Загрузка модели из JSON нужна для benchmark-фикстур.

### D. `serde` + writer в DOCX

**Суть:** `Model → JSON` для тестов, `Model → DOCX` для продукта.

**Почему отклонено:**

- Writer — это non-goal v1.
- Смешивает два разных решения в один ADR.
- Writer заслуживает отдельного ADR.
