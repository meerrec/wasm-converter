# ADR-0019: NodeId

**Статус:** Принято
**Дата:** 05.10.2026
**Контекст:** введение стабильных идентификаторов узлов в модели DOCX и XLSX
**Связанные ADR:** ADR-0003, ADR-0018

---

## Контекст

Модели DOCX и XLSX сегодня используют индексы в `Vec` как неявные идентификаторы узлов. Это создаёт проблемы:

1. **Hit-test** возвращает индекс, который меняет смысл при вложенных таблицах и floats. «Абзац №47» — это неоднозначно.
2. **Snapshot-тесты** `insta` шумят при изменении порядка обхода, даже если содержимое не изменилось.
3. **Отладка** по `tracing` не может сослаться на конкретный узел.
4. **Задел под редактирование** (ADR-0018) требует стабильных идентификаторов, но не editing-инфраструктуры.

При этом ADR-0018 явно запрещает в v1: command-паттерн, undo/redo, diff/patch, сериализацию для синхронизации, стабильность между сессиями.

`NodeId` должен дать пользу **сейчас** и не создавать обязательств на будущее.

---

## Решение

### 1. Формат

```rust
#[derive(Copy, Clone, PartialEq, Eq, Hash, Debug, Serialize, Deserialize)]
pub struct NodeId(u64);
```

- Не UUID. 8 байт на узел, не 16.
- Не строка. Сравнение и хеширование — O(1).
- Не глобально уникальный. Уникален в пределах одного открытия документа.
- Не переживает переоткрытие документа.

### 2. Где присваивается

`NodeId` присваивается **на этапе парсинга**, монотонным счётчиком:

```rust
struct NodeIdAllocator {
    next: u64,
}

impl NodeIdAllocator {
    fn new() -> Self {
        Self { next: 1 }  // 0 зарезервирован для корня
    }

    fn alloc(&mut self) -> NodeId {
        let id = NodeId(self.next);
        self.next += 1;
        id
    }
}
```

Аллокатор живёт в парсере. Один аллокатор на документ. Порядок присвоения — **порядок обхода XML** (document order). Это делает ID детерминированными для одного и того же входного файла.

### 3. Где живёт

`NodeId` присваивается:

- `Document` — корень, `NodeId(0)`;
- `Paragraph`;
- `Run`;
- `Table`;
- `Row`;
- `Cell`;
- `Section`;
- `Image` / `Anchor`;
- `Hyperlink`;
- `Bookmark`;
- `Field`;
- `Footnote` / `Comment`.

**Не** присваивается:

- `RawPPr` / `RawRPr` — это свойства, не узлы;
- `Style` — стили адресуются по `StyleId` (строка из XML);
- `Numbering` — адресуется по `NumId` / `AbstractNumId`;
- примитивы `Text`, `Break`, `Tab` внутри run — это контент, не узлы.

### 4. Вложенные структуры

Вложенные таблицы, floats, сноски получают ID в **общем** пространстве, не в иерархическом. То есть:

```
Document(0)
├── Paragraph(1)
│   └── Run(2)
│       └── Text("Hello")          — без ID
├── Table(3)
│   ├── Row(4)
│   │   └── Cell(5)
│   │       ├── Paragraph(6)
│   │       └── Table(7)           — вложенная, ID в том же пространстве
│   └── Row(8)
└── Paragraph(9)
```

Это даёт:

- плоский `HashMap<NodeId, NodeRef>` для быстрого доступа;
- возможность hit-test вернуть `NodeId` и не думать о пути;
- возможность `tracing` логировать `NodeId` без контекста.

Цена: `NodeId` не кодирует путь. Чтобы найти родителя, нужен обратный индекс или рекурсивный обход. Обратный индекс — `HashMap<NodeId, NodeId>` (parent), строится один раз после парсинга, если нужен.

### 5. Стабильность

| Свойство | Гарантия |
|---|---|
| Уникальность в пределах документа | Да |
| Детерминированность при одном входе | Да |
| Стабильность при переоткрытии | Нет |
| Стабильность при редактировании | Нет (не применимо в v1) |
| Стабильность между сессиями | Нет |
| Сериализация в JSON | Да (для отладки и тестов) |
| Сериализация в DOCX/XLSX | Нет (это запись, non-goal v1) |

### 6. Что `NodeId` НЕ даёт

- Command API.
- Undo/redo.
- Diff/patch.
- Стабильность между переоткрытиями.
- Синхронизацию.
- Возможность ссылаться на узел после закрытия документа.

Это **внутренний** идентификатор, не публичный API. Публичный API (React-обёртка, CLI) не должен его выставлять.

### 7. Использование

- **Snapshot-тесты** `insta`: `NodeId` включается в снапшот. При изменении порядка обхода тест падает — это правильно, потому что порядок обхода часть контракта парсера.
- **Hit-test:** `render::hit_test` возвращает `HitTarget::Node(NodeId)` вместо `HitTarget::Cell { row, col }`. `xlsx::paint::cellAtPoint` маппит `NodeId` → `Cell` через обратный индекс.
- **Отладка:** `tracing` логирует `NodeId` в событиях парсинга и layout.
- **Кэш каскада** (Спринт 9): ключ `(NodeId, StyleId)` вместо индексов.

## Последствия

### Положительные

1. **Полезно сразу.** Hit-test, snapshot-тесты, отладка — всё выигрывает.
2. **Дёшево.** 8 байт на узел, аллокатор — счётчик.
3. **Не создаёт обязательств.** Нет command-паттерна, undo/redo, diff.
4. **Детерминированность.** Один вход — одни ID.

### Отрицательные

1. **Обратный индекс.** Для поиска родителя нужен `HashMap<NodeId, NodeId>`, построенный после парсинга. Это дополнительная память (~8 байт на узел).
2. **Не сериализуется в DOCX.** При записи (если появится) ID нужно регенерировать.
3. **`NodeId(0)` для корня** — неявное соглашение, нужно задокументировать.

### Нейтральные

1. **`NodeId` — не публичный API.** React-обёртка его не выставляет.
2. **`NodeId` — не замена `StyleId`.** Стили адресуются строкой.

## Альтернативы

### A. UUID

**Почему отклонено:** 16 байт на узел, генерация дороже, детерминированность теряется. Не нужно в v1.

### B. Индексы в `Vec`

**Почему отклонено:** неоднозначны при вложенности, шумят в snapshot-тестах, ломаются при hit-test.

### C. Строковые пути (`"body/table[2]/row[1]/cell[3]/p[0]"`)

**Почему отклонено:** дорого, шумно, ломается при переименованиях.

### D. `NodeId` + иерархический путь

**Почему отклонено:** избыточно для v1. Если понадобится — обратный индекс даёт то же самое.
