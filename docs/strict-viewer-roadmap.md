# Программа «Строгий собственный просмотр DOCX/XLSX»

**Статус программы:** в работе  
**Дата принятия:** 21.11.2026  
**Последнее обновление плана:** 22.11.2026  
**Эпик первого этапа:** [#71](https://github.com/meerrec/wasm-converter/issues/71)

## 1. Цель и граница результата

Довести существующий Rust/WASM-вьюер до строгого визуального, текстового и постраничного соответствия Microsoft Word/Excel на явно определённой и сертифицированной матрице возможностей DOCX/XLSX.

Эталоном визуальной сверки являются заранее сохранённые снимки Office Online. Продукт использует только собственный движок и не требует установки или вызова Microsoft Office.

Строгое соответствие подтверждается отдельно для:

- текстового содержимого;
- шрифтов и shaping;
- переносов строк;
- геометрии блоков и объектов;
- числа страниц DOCX;
- экранного и печатного представления XLSX;
- присутствия и порядка объектов;
- цвета, границ, заливок и изображений;
- согласованности canvas, PDF и TextLayer.

Программа не обещает одинаковый результат для произвольного документа вне сертифицированной матрицы. Такие конструкции должны быть явно обнаружены и показаны пользователю как ограничение.

## 2. Принятые решения и ограничения

- [x] Вьюер только собственный: `crates/docx`, `crates/xlsx`, `crates/render`, существующие WASM-модули и `packages/core`.
- [x] Office Online Server, WOPI, Office iframe, desktop Office, LibreOffice-WASM, ONLYOFFICE и другие внешние движки просмотра не входят в продукт и тестовый runtime.
- [x] Office Online используется только при подготовке эталонных PNG и manifest.
- [x] Продукт и обычный CI работают автономно, без сетевых обращений к Office.
- [x] Strict OOXML и строгое визуальное соответствие рассматриваются как разные требования.
- [x] Допуск «±1 страница» не используется в сертифицированном режиме.
- [x] Средний SSIM не принимается как единственное доказательство соответствия.
- [x] Молчаливое удаление неподдерживаемого объекта запрещено: требуется `unsupported-visible` и запись в отчёт совместимости.
- [x] Границы ADR-0003/0007/0025 сохраняются; отдельный XLSX-layout crate не создаётся.

## 3. Как отмечать прогресс

Используются стандартные GitHub-чекбоксы:

- `[ ]` — работа не начата или не завершена;
- `[x]` — Definition of Done выполнен и подтверждён артефактами;
- `(в работе)` рядом с чекбоксом — задача начата, но ещё не завершена;
- `(заблокировано: причина)` — выполнение невозможно без указанного решения.

Правила обновления:

1. Чекбокс отмечается только после выполнения всех критериев приёмки конкретного пункта.
2. Рядом с завершённым пунктом добавляется ссылка на PR/commit и, при наличии, отчёт или тестовый артефакт.
3. При старте работы обновляются статус этапа и поле «Последнее обновление плана».
4. Сводная таблица обновляется вместе с чекбоксами.
5. Закрытие GitHub issue без выполненного DoD не считается завершением пункта roadmap.
6. Новые возможности сначала добавляются в матрицу совместимости, затем получают фикстуры и критерии приёмки.
7. Обновление эталонных изображений выполняется отдельным явным PR и никогда не происходит автоматически в обычном тестовом прогоне.

## 4. Целевой технический контур

```text
Продукт:

DOCX/XLSX
  → собственный parser
  → модель документа + feature report
  → собственный layout engine
  → Layout IR с позиционированными глифами и объектами
  → WASM/canvas + PDF + TextLayer/hit testing

Подготовка тестов:

фикстура → Office Online → reference PNG + manifest.json
фикстура → наш вьюер    → actual PNG + runtime metadata
reference + actual     → автономный diff → report.json + report.html
```

После подготовки эталонов разработка и CI не требуют Office. Харнесс обязан отличать дефект движка от ошибки захвата и неправильного эталона.
