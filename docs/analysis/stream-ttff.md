# ReadableStream и Time to First Frame: где проходит граница

**Дата:** 03.11.2026
**Контекст:** issue #57; [ADR-0031](../adr/0031-streaming-zip.md) (потоковый
вход), [ADR-0049](../adr/0049-stream-chunk-append.md) (поштучный append),
[ADR-0046](../adr/0046-format-plugin-contract.md) (ленивые модули форматов).
**Метод:** разбор ADR и кода по узлам. Замеров TTFF в браузере здесь нет:
утверждения о пути подтверждены кодом, а не таймингом. Существующие числа
(ROADMAP, §Спринт 4; `crates/wasm/tests/painter_perf.rs`) относятся к сборке и
отрисовке кадра, а не к TTFF.

## 1. Короткий вывод

Тезис «внедрение `ReadableStream` решает проблему TTFF» в общем виде неверен.
Потоковый вход — транспорт: он не делает рендер прогрессивным и не позволяет
начать парс раньше последнего байта. Для ZIP-форматов это запрещено самим
форматом: central directory лежит в конце архива, а `ZipArchive` без него не
открывается ([ADR-0031, §«Контекст»](../adr/0031-streaming-zip.md#L18-L21)).
TTFF снизу ограничен полным приходом пакета и построением модели: у DOCX и ODT
— ещё и полной раскладкой, у PPTX и ODP — раскладкой всех слайдов, у книг —
разбором всех листов.

Что паттерн действительно даёт:

- main-поток держит один чанк, а не файл; чанк, владеющий буфером, уезжает
  переводом владения без копии
  (`packages/core/src/render/open_stream.ts:65-74`);
- прогресс и отмену загрузки до парса
  ([ADR-0031, §«Последствия»](../adr/0031-streaming-zip.md#L86-L87));
- на холодном открытии ленивого формата загрузка wasm-модуля стартует в
  `open-stream` и идёт параллельно приёму файла
  (`packages/core/src/worker/docx_worker.ts:54-77`); на пути через
  `ArrayBuffer` модуль грузится только после прихода всего файла
  (`docx_worker.ts:99-104`) — это единственный настоящий выигрыш TTFF от
  потокового входа;
- ADR-0049 снимает с конца потока копию JS→wasm, если модуль успел
  загрузиться раньше конца приёма; если модуль медленнее сети, копия
  по-прежнему случается в `end-stream`
  (`packages/core/src/worker/worker_core.ts:615-637`).

Точная формулировка: **`ReadableStream` перекрывает загрузку модуля и копию в
wasm с приёмом файла; первый кадр всё равно ждёт последний байт и построения
модели.**

## 2. Критический путь первого кадра

TTFF здесь — от вызова `viewer.open()` до первой отрисовки кадра (в примерах
видно по `onTick`). Путь по узлам:

| Узел | Где | Снимает ли поток / ADR-0049 |
| --- | --- | --- |
| Инициализация сессии: painter и шрифты до `ready` (один раз на воркер) | `worker_core.ts:305-308`, `render_offscreen.ts:82`, `fonts.ts:62-101` | нет |
| Старт загрузки ленивого модуля | `docx_worker.ts:54-77`, `pptx_worker.ts:88-95` | да: параллельно приёму файла |
| Приём пакета | `open_stream.ts:34-90` | это и есть поток |
| Копия JS→wasm | `worker_core.ts:615-637`, `crates/wasm-common/src/streams.rs:40-52` | да, если модуль уже готов |
| Ожидание модуля в `end-stream` | `worker_core.ts:495` | перекрыто приёмом файла |
| Сборка `source` | `worker_core.ts:510-533` | нет; join убирается подсказкой `size` |
| Парс пакета | [ADR-0031, §4](../adr/0031-streaming-zip.md#L38-L39); `crates/docx-wasm/src/stream_api.rs:57-65` | нет |
| Построение модели | `crates/docx-wasm/src/docx_api.rs:78-101`, `crates/pptx-wasm/src/pptx_api.rs:3-5`, `crates/xlsx/src/lib.rs:243-300` | нет |
| Декодирование всех картинок | `worker_core.ts:651-665`, `crates/docx-wasm/src/docx_api.rs:238-245` | нет: политика `finishOpen` |
| Ответ → rAF main → `render` | `viewer_core.ts:349-357`, `docx_viewer.ts:223-230` | нет |
| Сборка DisplayList | `frame_loop.ts:74`, `xlsx_api.rs:173-198`, `docx_api.rs:320-330` | нет |
| Отрисовка на rAF | `frame_loop.ts:94` | нет |

Порядок жёсткий. `end-stream` дожидается `moduleReady`, собирает `source`,
затем вызывает `finishStream` — синхронный парс в потоке воркера
(`worker_core.ts:534-539`; [ADR-0031, §4](../adr/0031-streaming-zip.md#L38-L39)).
У DOCX там же считается полная раскладка: `install_document` зовёт
`layout_document_with_cancel` (`docx_api.rs:78-101`); ODT раскладывает документ
при открытии по тому же принципу (`crates/odt-wasm/src/odt_api.rs:3-5`).
У PPTX и ODP раскладка всех слайдов тоже выполняется при открытии
(`pptx_api.rs:3-5`, `odp_api.rs:3-5`). У книг
`open_archive` разбирает все листы, `sharedStrings`, стили, тему и media
(`crates/xlsx/src/lib.rs:243-300`); раскладка листа считается лениво, при
первой сборке кадра (`crates/xlsx/src/paint.rs:189-197`).

Только после этого `finishOpen` декодирует **все** картинки документа
(`worker_core.ts:651-665`) и отвечает `opened`. Main применяет страницы и
планирует `render` на ближайшем rAF (`docx_viewer.ts:223-230`,
`viewer_core.ts:349-357`). Воркер собирает кадр в микрозадаче
(`frame_loop.ts:74`), painter рисует его на следующем rAF
(`frame_loop.ts:94`).

Отсюда нижняя граница для ZIP-форматов:

```text
TTFF ≥ последний байт (EOCD)
     + построение модели (у DOCX/ODT — полная раскладка)
     + декодирование всех картинок
     + один кадр main (rAF) + сборка + один кадр painter (rAF)
```

Потоковый вход не сокращает ни одно слагаемое после последнего байта, кроме
финальной копии — и только когда она успела пройти раньше.

## 3. Что именно даёт ADR-0049

1. **Владение чанком.** Если чанк занимает свой `ArrayBuffer` целиком, main
   отдаёт его переводом владения: копии на main нет. Вью поверх большего
   буфера копируется только своим срезом — transfer унёс бы соседние байты
   (`open_stream.ts:65-74`).

2. **Поштучный догон.** `flushStream` идемпотентен: счётчики `flushed` и
   `flushedChunks` не дают отправить байт дважды, а подписка на `moduleReady`
   продолжает работу уже после того, как модуль выставил `streamId`
   (`worker_core.ts:410-424`, `615-637`). Порядок чанков задан счётчиками, а
   не таймингом.

3. **Копия распределена.** В wasm каждый чанк стоит двух копий: обвязка
   wasm-bindgen копирует `Uint8Array` в память wasm, затем
   `SegmentedBuffer::append` делает `to_vec`
   (`crates/core/src/chunk_reader.rs:46-53`). Суммарный объём копий тот же,
   что при одном большом append, но размазан по загрузке; вторую копию можно
   убрать, если `stream_append` будет принимать `Vec<u8>`/`Box<[u8]>` и
   складывать владение без `to_vec`.

4. **Пик памяти не меняется.** Путь с `totalSize` — `target` на весь вход плюс
   сегменты в wasm; путь без размера — `chunks` плюс join плюс сегменты
   (`worker_core.ts:510-533`; [ADR-0049, §«Пик памяти»](../adr/0049-stream-chunk-append.md#L75-L81)).
   Меняется длительность пика, а не его величина.

5. **Выигрыш условен.** Копия уходит с критического пути только в той части,
   что пришла после готовности модуля. Если модуль грузился дольше файла,
   `end-stream` досылает всё накопленное — ровно прежнее поведение. Для
   холодного открытия ленивого формата на быстрой сети выигрыш стремится к
   нулю; для повторного открытия с тёплым модулем копия перекрыта приёмом
   полностью.

6. **Начало парса не сдвинулось.** `finishStream` вызывается на `end-stream`
   (`worker_core.ts:534-539`). Формулировка ADR-0049 «парс может начаться
   раньше» верна лишь в смысле «раньше на время финальной копии», а не
   «раньше последнего байта».

## 4. Что остаётся за пределами паттерна

- **Полный приход пакета.** Central directory ZIP в конце; `SegmentedBuffer`
  лишь копит чанки и умеет `Read + Seek` в пределах накопленного
  (`crates/core/src/chunk_reader.rs:1-6`, `120-140`).
- **Контракт «целая модель».** `FormatPlugin::parse` принимает байты и
  возвращает целую модель (`crates/render/src/plugin.rs:159-181`); потоковый
  путь повторяет это в per-format `stream_open_*` через
  `parse_docx_segmented`/`open_segmented`, не меняя контракт
  ([ADR-0031, §6](../adr/0031-streaming-zip.md#L49-L59)).
- **Полная раскладка.** DOCX/ODT раскладывают весь документ при открытии;
  PPTX/ODP — все слайды. Кадр потом лишь выбирает видимые страницы из готовой
  раскладки (`docx_api.rs:281`).
- **Все картинки.** `finishOpen` ждёт `loadBitmaps` для всего списка медиа
  (`worker_core.ts:651-665`), хотя painter молча пропускает незарегистрированный
  битмап (`crates/render/src/painter/painter_2d.rs:227-231`). Это политика, а
  не техническая необходимость.
- **Оркестрация.** Первый `render` уходит после ответа `opened` и ближайшего
  rAF; на первом открытии запрос не может быть отправлен раньше, потому что
  `renderMsg` возвращает `null`, пока список страниц/листов/слайдов пуст
  (`docx_viewer.ts:369-377`, `xlsx_viewer.ts:255-257`,
  `pptx_viewer.ts:208-210`).

## 5. Что действительно сдвигает TTFF

Порядок — по отношению «эффект / цена».

### 5.1. Не ждать картинки до первого кадра

Сейчас `finishOpen` декодирует все медиа до ответа `opened`
(`worker_core.ts:651-665`; список — все медиа документа,
`crates/docx-wasm/src/docx_api.rs:238-245`). Painter пропускает
незарегистрированный битмап, поэтому кадр без картинок технически возможен
(`painter_2d.rs:227-231`).

Изменение: ответить `opened` сразу после модели, собрать первый кадр без
картинок, дорисовать их по мере декодирования (поколение `bitmapsGen` и
`dropBitmaps` уже сторожат смену документа). Цена: картинки появляются позже;
на насыщенном изображениями первом экране будет пустое место. Эффект: из TTFF
уходит сумма декодирования **всех** медиа, а не только видимых.

### 5.2. Передавать `size`, когда он известен

Без `totalSize` воркер собирает чанки в JS и на `end-stream` склеивает их в
новый `Uint8Array` — полная копия после последнего байта, то есть на
критическом пути (`worker_core.ts:510-533`). С `totalSize` буфер
предвыделяется, заполняется по месту и уходит в парс без join
(`worker_core.ts:520-522`). Примеры уже передают `size` из `Content-Length`
(`examples/viewer/e2e/stream.spec.ts:44`); это правило стоит закрепить для
всех вызовов, где размер известен.

### 5.3. Убрать кадр main между `opened` и `render`

`finishOpen` просит кадр только если запрос уже пришёл
(`worker_core.ts:665`); на первом открытии `pending` пуст, и `render` уходит
на ближайшем rAF после ответа (`docx_viewer.ts:223-230`). Если main отправит
начальный `render` вместе с `open` (вьюпорт известен из canvas), воркер
соберёт первый кадр сразу из `finishOpen`. Эффект — до одного кадра экрана
(≈16,7 мс при 60 Гц); цена — аккуратно снять запрос при ошибке открытия.

### 5.4. Прогрессивная модель: сначала единица рендера 0

Это единственный способ получить первый кадр **до** последнего байта или до
разбора всего пакета. Возможность по форматам:

| Формат | Части пакета | Что нужно для кадра 0 | Блокер |
| --- | --- | --- | --- |
| PPTX | слайды отдельными частями `ppt/slides/slideN.xml` (`crates/pptx/src/parse.rs:5`) | `presentation.xml` + rels + slide1 + layout + master + theme + media слайда | `parse` читает все слайды, раскладка всех при открытии (`pptx_api.rs:3-5`) |
| ODP | один `content.xml` | префикс до первого `draw:page` + `styles.xml` | `content.xml` парсится целиком |
| ODS | один `content.xml` | префикс до первого листа + `styles.xml` | то же |
| ODT | один `content.xml` | префикс потока + `styles.xml` (страничные стили) | то же + потоковая раскладка |
| DOCX | один `word/document.xml` | префикс + `styles`/`numbering`/`theme` | финальный `w:sectPr` в конце `w:body` задаёт размер и поля страницы (`crates/docx/src/document.rs:260-264`) — без конца части геометрия страницы 1 неизвестна |
| XLSX | листы отдельными частями `xl/worksheets/sheetN.xml` | `workbook` + rels + префикс sheet1 + `styles` + `sharedStrings` + theme | `open_archive` разбирает все листы (`crates/xlsx/src/lib.rs:274-295`) |
| XLSB | листы `xl/worksheets/sheetN.bin` (`crates/xlsb/src/lib.rs:14-16`) | `workbook.bin` + rels + sheet1.bin + стили | та же модель книги |

PPTX — самый дешёвый кандидат: слайд отделён от остальных частей. ODF и
DOCX делят содержимое одного XML-парта; ODF ещё допускает префиксный разбор
(автоматические стили идут до тела), DOCX упирается в `sectPr` в конце.
XLSX/XLSB имеют отдельные части листов, но глобальные `sharedStrings` и стили
читаются целиком.

Любой вариант требует нового контракта: `parse` должен уметь отдать первую
единицу рендера раньше остальных, а не только принимать байты иначе. Это
правка `FormatPlugin`/модели, а не транспорта.

### 5.5. Range-запросы вместо полной загрузки

`SegmentedBuffer` — `Read + Seek` по уже полученным чанкам; `Seek` за
`total` запрещён, догружать он не умеет (`chunk_reader.rs:120-140`). Для
удалённого ZIP нужен разреженный источник: EOCD и central directory берутся
хвостом, затем нужные части — Range-запросами. Но парс синхронный
(`plugin.rs:177-181`), а HTTP в wasm асинхронен: понадобится либо асинхронная
предзагрузка нужных частей до синхронного парса, либо асинхронный контракт
парса. Без 5.4 выигрыша нет: текущий парсер всё равно прочитает все части,
и набор предзагрузки выродится в весь файл.

### 5.6. Прогрев модуля и шрифтов

Модуль ленивого формата можно грузить заранее, до действия пользователя;
шрифты уже регистрируются один раз до `ready` (`worker_core.ts:305-308`,
`render_offscreen.ts:82`, `fonts.ts:62-101`), и откладывать их нельзя:
промах по `ctx.font` запоминается на сессию воркера
(`fonts.ts:90-92`). В потоковом пути загрузка модуля уже перекрыта приёмом
файла; прогрев даёт выигрыш пути через `ArrayBuffer` и медленного модуля.

## 6. Граница понятий

| Утверждение | Вердикт |
| --- | --- |
| «`ReadableStream` решает TTFF» | Нет: рендер не становится прогрессивным, парс не начинается раньше последнего байта |
| «`ReadableStream` перекрывает загрузку модуля и копию с приёмом файла» | Да, при условии, что модуль готов раньше конца потока |
| «TTFF можно улучшить, не трогая поток» | Да: картинки (5.1), `size` (5.2), кадр main (5.3) |
| «Ранний первый кадр требует прогрессивной модели» | Да: транспорт сам по себе не даёт кадр раньше конца пакета |

Для «Runtime Edit Live» вывод тот же по природе: правка run'а перезапускает
полную раскладку документа синхронно (`docx_api.rs:148-174`), поэтому отклик
правки упирается в тот же контракт «целая модель», а не в скорость доставки
байтов.

## 7. Формулировка для ячейки 42

> Архитектурный разбор интеграции `ReadableStream` (ADR-0031 + ADR-0049).
> Потоковый вход сам по себе не решает Time to First Frame: ZIP-пакет нельзя
> разобрать раньше последнего чанка (central directory лежит в конце), а
> модель строится целиком — у DOCX и ODT с полной раскладкой, у PPTX и ODP с
> раскладкой всех слайдов, у книг с разбором всех листов. Что даёт интеграция:
> main держит чанк вместо файла; появляются прогресс и отмена до парса; на
> холодном открытии ленивого формата загрузка wasm-модуля идёт параллельно
> приёму файла; ADR-0049 убирает с конца потока копию JS→wasm, если модуль
> успел загрузиться. Пик памяти не меняется — меняется его длительность. TTFF
> по-прежнему определяют полный приход пакета, построение модели, ожидание
> всех картинок в `finishOpen` и один кадр main до запроса рендера. Ранний
> первый кадр — отдельная задача прогрессивной модели, а не следствие
> `ReadableStream`.

## 8. Что осталось непроверенным

- Замеров TTFF «в браузере» нет: путь разобран по коду. Для чисел нужен
  прогон «холодный/тёплый модуль × поток/буфер × фикстуры разного размера» с
  разделением парса, раскладки, картинок и оркестрации.
- Продуктовый вопрос 5.1: допустим ли первый кадр без картинок.
- Стоимость прогрессивной модели по форматам (5.4) не оценена: неизвестно,
  сколько времени уходит на разбор/раскладку единицы 0 против всего
  документа; без этого нельзя выбрать формат-первопроходец.
