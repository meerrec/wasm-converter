## H1. Размер wasm + data по сети — 49,97 МиБ → **нет**

**Чем снято.** CDP-сессия на странице (`context.newCDPSession(page)`),
`Network.enable`, затем сумма `encodedDataLength` из событий
`Network.loadingFinished` по URL артефактов. Это фактически принятые байты, а не
заголовок `content-length` (который для `soffice.js` вообще отсутствует —
ответ чанками). Перекрёстная проверка — `content-length` из
`Network.responseReceived.response.headers` и сумма `dataLength` из
`Network.dataReceived` (несжатый размер).

| Артефакт | По сети (CDP) | `content-length` | Сжатие | Разжато | Протокол |
|---|---|---|---|---|---|
| `soffice.js` | 172 569 Б | — (чанками) | **zstd** | 858 124 Б | h2 |
| `soffice.wasm` | 36 320 413 Б | 36 279 250 Б | br | 161 667 499 Б (154,2 МиБ) | h2 |
| `soffice.data` | 15 909 446 Б | 15 891 013 Б | br | 99 520 604 Б (94,9 МиБ) | h2 |
| **Итого** | **52 402 428 Б = 49,97 МиБ** | | | 261,9 МиБ разжатых | |

Вспомогательные запросы того же демо (в сумму выше не входят):
`soffice.data.js.metadata` — 216 132 Б, `zetaHelper.js` — 4 169 Б, HTML — 2 290 Б,
`zeta.js` — 10 380 Б. Полный конверт с ними: **50,18 МиБ**.

**Вердикт: «нет»** — 49,97 МиБ при пороге «нет» > 40 МиБ.

**Поправка к разведке.** Разведка сообщала «`soffice.js` = 858 124 Б, всегда
brotli». Оба утверждения неверны: 858 124 Б — это **разжатый** размер, по сети
же идёт 172 569 Б, и сжат он **zstd**, а не brotli (Chromium 153 предлагает
`Accept-Encoding: … br, zstd`, CDN выбирает zstd). На вердикт это не влияет:
вес дают `soffice.wasm` и `soffice.data`, и он подтверждён точно.

Число стабильно: 49,97 МиБ в обоих прогонах и во всех пяти дополнительных.

## H2. Холодный старт — 17,85 / 14,62 с → **нет**

**Что считается готовностью.** `input.disabled === false`. Это не догадка:
в `office_thread.js` воркер после инициализации `ZetaHelperThread` (созданы
`Desktop`, `ReadWriteAccess` и т. п.) шлёт `{cmd:'start'}`, а обработчик в
разметке демо на этот случай делает `input.disabled = false`. То есть снятие
`disabled` = «UNO-контекст поднят и готов принять `convert`».

**Чем снято.** `addInitScript`, который ставит `MutationObserver` на появление
`#input` и на снятие атрибута `disabled`, и пишет `performance.now()`. Метки
внутри страницы — в одной шкале с Resource Timing, поэтому «сеть» и
«инициализация CPU» разделяются без выравнивания часов CDP.

Разделение фаз: сеть = от `startTime` первого артефакта до `responseEnd`
последнего (Resource Timing); CPU-инициализация = от `responseEnd` последнего
артефакта до снятия `disabled` (компиляция wasm, распаковка `.data`, старт Qt/UNO).

| Прогон | Готовность | Сеть | CPU-инициализация |
|---|---|---|---|
| Холодный №1 | **17 845 мс** | 15 675 мс | 2 125 мс |
| Холодный №2 | **14 621 мс** | 12 300 мс | 2 251 мс |

Разбивка по артефактам (холодный №1): `soffice.js` 45→1811 мс (1765 мс),
`soffice.wasm` 1820→10 923 мс (9103 мс), `soffice.data` 11 547→15 720 мс (4173 мс).

**Вердикт: «нет».** В порог «да» (≤ 8 с) не уложился ни один прогон, причём
неустранимо: **одна сеть** занимает 12,3–24,6 с, то есть больше 8 с ещё до
любой работы CPU. Формальный порог «нет» (> 20 с) пройден в двух прогонах из
семи (22,16 с и 28,08 с); остальные пять (14,6–18,4 с) — в серой зоне.

**Ключевое:** CPU-инициализация мала и стабильна (1,9–2,3 с во всех семи
прогонах). Холодный старт — это почти целиком **скачивание 50 МБ**, а не
разбор модуля.

### Разброс (все прогоны, одна методика)

7 независимых холодных стартов: **28,08 / 22,16 / 18,40 / 17,85 / 17,43 / 16,53 / 14,62 с**.
Разброс 1,9× — сама по себе величина нестабильная, и её «хвост» уже переходит
границу «нет».

## H3. Тёплый старт — 11,78–16,49 с → **нет**

**Что считалось тёплым.** Перезагрузка той же страницы в том же контексте
браузера после полного холодного старта: HTTP-кэш прогрет, V8-кэш
скомпилированного wasm тоже, а документ и воркеры стартуют заново. Это
«второй визит» пользователя.

**Чем снято.** То же измерение готовности, что и в H2, плюс пофазный учёт сети
через CDP (`Network.loadingFinished`), чтобы увидеть, что именно берётся из кэша.

| Прогон | Тёплый №1 | Тёплый №2 |
|---|---|---|
| Холодный №1 | **16 490 мс** | **12 878 мс** |
| Холодный №2 | **12 159 мс** | **11 779 мс** |

**Причина — сеть никуда не девается.** В каждом тёплом прогоне по сети снова
идёт **52 229 425–52 230 766 Б**, то есть ровно тот же объём, что и на холоде:

| Ресурс | Тёплый №1 | Тёплый №2 |
|---|---|---|
| HTML демо | 0 Б (из кэша) | 0 Б |
| `zetaHelper.js` (4 КБ) | 0 Б (из кэша) | 0 Б |
| `soffice.js` (173 КБ) | **0 Б (из кэша)** | **0 Б** |
| `soffice.data.js.metadata` (216 КБ) | **0 Б (из кэша)** | **0 Б** |
| `soffice.wasm` (36,3 МБ) | **36 320 620 Б (заново)** | **36 320 007 Б (заново)** |
| `soffice.data` (15,9 МБ) | **15 909 426 Б (заново)** | **15 909 418 Б (заново)** |

То есть кэш **исправно работает** для всего, что до ~216 КБ, и не срабатывает
ровно на двух крупных файлах. CDN при этом отдаёт их как кэшируемые:
`cache-control: public, max-age=1200`. Запросы идут без `Cache-Control`,
`Pragma` и `Range` — то есть без признаков намеренного обхода кэша со стороны
загрузчика.

**Проверка, что это не артефакт стенда.** Прогон с
`--disk-cache-size=2000000000` (2 ГБ на кэш вместо умолчания) поведения не
изменил: тёплые старты 17 543 и 13 070 мс, те же 52 232 539 Б по сети. Командная
строка запущенного браузера (снята с `chrome://version`) не содержит ни
`--disable-http-cache`, ни `--disk-cache-dir`, ни иных переключателей кэша, —
единственное совпадение по маске `--*cache*` это `--user-data-dir`.

**Вердикт: «нет».** Все четыре тёплых старта > 8 с (порог «нет»), и ни один не
близок к «да» ≤ 3 с. Практический вывод для проекта: **повторный визит не
дешевле первого** — ~50 МБ и ~12–16 с платятся каждый раз.

Механизм (почему два крупных файла не кладутся в кэш при исправно работающем
кэше) **не установлен**: похоже на порог по размеру записи в HTTP-кэш Chromium,
но прогон с 2 ГБ его не подтвердил. Это отдельный вопрос к следующему слайсу
(и его стоит перепроверить в Firefox/WebKit: возможно, там поведение иное).

## H4. Пик памяти — 2193,6 МБ → **нет**

`crossOriginIsolated === true` на этой странице, поэтому доступен
предпочтительный путь — `performance.measureUserAgentSpecificMemory()`. Он
учитывает память wasm (в отличие от JS-heap), поэтому основное число — его.

**Чем снято (основное).** `page.evaluate(() => performance.measureUserAgentSpecificMemory())`
в трёх точках. Значения в МБ, `bytes / 1048576`.

| Точка | Что это | Память (API) | JS-heap | Атрибуция |
|---|---|---|---|---|
| **P0** | оболочка демо **без модуля** | **0,7 МБ** | 1,3 МБ | `about:blank` 0,2 + демо 0,2 + Shared 0,3 |
| **P1** | после готовности (`disabled=false`) | **2185,3 МБ** | 113,2 МБ | страница **1132,7** + воркер **1051,9** + Shared 0,5 |
| **P2** | после конвертации DOCX→PDF | **2193,6 МБ** | 183,0 МБ | — |
| **P3** | после выгрузки PDF | **2193,9 МБ** | 135,7 МБ | — |

Как получен P0: та же страница демо, но загрузка артефактов запрещена
(`Network.setBlockedURLs(['*soffice*'])`). Иначе «до старта» не поймать —
`measureUserAgentSpecificMemory()` сам по себе не мгновенный и на живом
документе попадает уже после начала загрузки. В P0 `input.disabled` остаётся
`true`, то есть модуль действительно не поднялся.

**Как читать числа.** P0 = 0,7 МБ снимает вопрос о накладных расходах: пустая
оболочка демо не стоит ничего, все ~2,2 ГБ — это модуль. Два блока по ~1 ГБ
(страница и `blob:`-воркер `em-pthread`) атрибутированы как `JavaScript` — это
линейные памяти wasm. Из документа почти ничего не добавляется: **P2 − P1 =
8,3 МБ** на файл в 5,9 МБ. То есть память определяется модулем, а не
документом, и от размера документа почти не зависит.

**Перекрёстная проверка (грубее, но по ОС).** RSS рендереров браузера,
семплирование `ps -axww -o pid,ppid,rss,args` каждые 200 мс. Процессы
опознаются по своему `--user-data-dir` (его несут и helper-процессы), поэтому
браузеры, запущенные параллельно другими слайсами, в сумму не подмешиваются.

| Фаза | Пик суммы рендереров | Крупнейший рендерер | Процессов |
|---|---|---|---|
| загрузка модуля | 1017,5 МБ | 798,7 МБ | 3 |
| **конвертация (P1 → PDF)** | **1269,6 МБ** | **738,8 МБ** | 5 |
| тёплые перезагрузки | 1240,4 МБ | 1051,3 МБ | 3 |

Во втором прогоне: 832,8 МБ на загрузке и 1233,5 МБ на перезагрузках
(крупнейший рендерер 1051,5 МБ). Лишние рендереры в фазе конвертации — это
встроенный просмотрщик PDF (`chrome-extension://mhjfbmdgcfjbbjbbpaeojofohoefgiehjai/pdf_embedder.css`
виден в сети), он же служит подтверждением, что полученный PDF действительно
отрисован браузером.

**Вердикт: «нет».** 2193,6 МБ > 1,5 ГБ. API-число воспроизводится бит в бит
(2185,3 МБ в P1 во всех прогонах). RSS-оценка ниже (1,23–1,27 ГБ) — она
считает реально тронутые страницы, тогда как API отдаёт полный размер
зарезервированной линейной памяти; даже по ней порог «да» 800 МБ превышен, но
формально 1,5 ГБ не достигается. **Решающим считаю API-число**, и оно даёт «нет».

Оговорка: инструментальный перехват PDF-блоба (`URL.revokeObjectURL` заменён на
no-op) держит блоб живым между P2 и P3, то есть завышает эти две точки. Это
несущественно: сам блоб — 4,8 МБ при 2193,6 МБ общей памяти.

## H5. Конвертация фикстуры — 4,62 с → **да**

**Чем снято.** `page.setInputFiles('#input', <фикстура>)`, затем метки времени в
странице: перехват `MessagePort.prototype.postMessage` (момент отправки
`{cmd:'convert'}`) и подмена сеттера `MessagePort.prototype.onmessage` (момент
прихода `{cmd:'converted'}`). Всё в часах `performance.now()`.

Фикстура: `test-fixtures/СУС УТП_v2.0_31.10.25.docx`, 5 937 643 Б.

| Величина | Значение |
|---|---|
| `change` → `convert` отправлен (чтение файла + запись в FS) | 6–21 мс |
| **В воркере: `convert` → `converted`** | **4620 мс** |
| Всего от `change` до `converted` | 4626 мс |

По всем прогонам рабочей версии инструмента: 4443 / 4449 / 4564 / 4568 /
4620 / 4626 / 4658 / 4668 / 4802 мс — то есть 4,4–4,8 с стабильно.

**Вердикт: «да»** — 4,62 с при пороге «да» ≤ 20 с, с запасом 4×.
Замер сделан на уже поднятом модуле (после готовности), то есть это чистая
стоимость конвертации 5,9 МБ DOCX, без холодного старта.

**Выходной PDF** (важный артефакт слайса):
`/tmp/lowa-measure/sus-utp-zetaoffice.pdf`, **4 791 564 Б**.
`file` → `PDF document, version 1.7`; открывается (`pdfinfo`): 161 страница,
Producer `ZetaOffice 24.2`, Creator `Writer`, Tagged: yes, JavaScript: no.

## Консоль браузера

Конвертация проходит **без единой ошибки страницы**: `pageerror` = 0,
ответов HTTP ≥ 400 = 0, `requestfailed` = 0 во всех прогонах.

`console.error` содержит 18–26 записей, все — шум самой сборки и Chromium, не

- 14× `QObject::connect(QWindow, QtFrame): invalid nullptr parameter`
- 6× `QRect(0,0 0x0) 1`

влиял. Демо рабочее, подписки не требует, оверлеев и блокировок нет.

## Что не снято и почему

1. **CPU-время конвертации в отрыве от стены** — не снималось. У LOWA на этом
   стенде нет способа получить per-task CPU; `Performance.getMetrics` на
   странице не видит воркера, где идёт вся работа. Стенных 4,6 с для H5
   достаточно, но если понадобится «сколько именно CPU», понадобится отдельный
   заход.
2. **Механизм отказа кэша на двух крупных файлах** — не установлен (см. H3).
   Факт зафиксирован, причина нет.
3. **Причина расхождения API-памяти и RSS** — не разбиралась до конца.
   Предположение: API отдаёт размер зарезервированной линейной памяти wasm,
   RSS — тронутые страницы. Проверка потребовала бы доступа к внутренним
   счётчикам памяти wasm из воркера.

## Отклонения от постановки

- **P0 снимается не на той же загрузке страницы, а на второй (той же страницы с
  заблокированными артефактами).** Так требовала сама методика: измерить память
  «до старта модуля» на живом документе нельзя — API сам по себе не мгновенный.
  Побочный эффект: HTML и `zetaHelper.js` успевают попасть в кэш от baseline-страницы,
  поэтому в холодной фазе они приходят за 0 байт (на H1 не влияет — артефакты
  не кэшированы, они скачиваются полностью).
- **Добавлен прогон с `--disk-cache-size`** (не было в постановке) — чтобы
  отличить свойство сборки от свойства стенда. Результат в H3.
- **RSS-процессы опознаются по `--user-data-dir`**, а не по PID-диффу: во время
  работы параллельно шли замеры других слайсов, и дифф подмешивал чужие
  браузеры (первые прогоны давали завышенные пики до 2,4 ГБ). В отчёте только
