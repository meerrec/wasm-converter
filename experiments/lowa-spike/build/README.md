# Сборка headless LibreOffice (LOWA) на внешней VM

Здесь лежит процедура сборки writer-only WASM-сборки LibreOffice core —
`soffice.js` + `soffice.wasm` + `soffice.data`. Это вход этапа B плана спринта 13
(`docs/sprint-13/plan.md`), слайс B1.

Сборка на рабочей машине не выполняется и не может: нужно ≥ 64 ГБ RAM
(апстрим в `static/README.wasm.md` прямо пишет, что линковка «possibly needs
64GB RAM»), несколько десятков гигабайт диска и Linux. Скрипт рассчитан на
арендованную Linux-VM.

## Требования к машине

| Параметр | Значение | Откуда |
|---|---|---|
| ОС | Linux x86_64 (Debian/Ubuntu проверяемы; пакеты — см. сообщение скрипта) | скрипт проверяет `uname -s` |
| RAM | ≥ 64 ГБ (скрипт откажется работать меньше, обход — `ALLOW_UNDERSPEC=1`) | README апстрима |
| vCPU | 16–32 (скрипт берёт `nproc`, переопределяется `JOBS`) | план спринта, §5 |
| Диск | ≥ 200 ГБ SSD; жёсткий минимум скрипта — 120 ГБ свободных | план спринта, §5; оценка, уточняется прогоном |
| Сеть | исходящий доступ к GitHub, dev-www.libreoffice.org, download.documentfoundation.org | `make fetch` |
| Инструменты | git, make, gcc/g++, flex, bison, autoconf, automake, pkg-config, python3, perl, curl, unzip, zip, patch | проверяются на шаге 0, список печатается целиком |

Оценка времени (README апстрима время не нормирует — ориентир, уточняется
первым прогоном): клон LO и загрузка внешних tarballs — 15–40 мин, компиляция
и линковка на 16–32 vCPU — порядка 2–5 ч, из них заметная доля приходится на
единственный линк `soffice_bin`, который идёт почти без параллелизма. Один
прогон целиком — «полдня аренды» с запасом; в плане спринта под B1 отведён
день, и второй прогон (воспроизводимость) идёт следом на чистой VM.

## Запуск

```bash
# на VM, от пользователя с правами на $HOME
git clone --depth 1 --branch sprint/13-lowa-spike <репозиторий> doc-converter   # или scp одного файла
bash doc-converter/experiments/lowa-spike/build/build-lowa.sh 2>&1 | tee /tmp/lowa-run.txt
```

Скрипт сам скачает emsdk и исходники, соберёт и сложит артефакты. Ничего в
репозитории не создаётся: рабочая область — `$BUILD_ROOT` (по умолчанию
`$HOME/lowa-build`), туда же пишется лог прогона.

Все параметры задаются переменными окружения перед командой:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BUILD_ROOT` | `$HOME/lowa-build` | всё скачанное и собранное |
| `EMSDK_VERSION` / `EMSDK_COMMIT` | `4.0.10` / `62a853c…` | пин тулчейна |
| `LO_TAG` / `LO_COMMIT` | `libreoffice-26.8.1.1` / `f3b61cf…` | пин исходников |
| `WASM_MODULE` | `writer` | `--with-wasm-module` |
| `PROXY_TO_PTHREAD` | `1` | `0` → `--disable-emscripten-proxy-to-pthread` (развилка для замера H2/H3) |
| `JSPI` | `0` | `1` → `--enable-emscripten-jspi` (экспериментально) |
| `DISABLE_LTO` | `0` | `1` → `--disable-lto`: аварийный рычаг против OOM на линковке |
| `EXTRA_LDFLAGS` | пусто | дописать флаги к `gb_EMSCRIPTEN_LDFLAGS` (патч с маркером, снимается сам) |
| `EXTRA_CONFIGURE_FLAGS` | пусто | прочие флаги configure одной строкой |
| `ENABLE_CCACHE` | `0` | `1` → `--enable-ccache`, если ccache есть |
| `JOBS` | `nproc` | параллелизм make |
| `MIN_RAM_GB` / `MIN_DISK_GB` / `ALLOW_UNDERSPEC` | `64` / `120` / `0` | пороги и обход предусловий |

Перезапуск на той же VM безопасен: повторный прогон видит уже установленный
emsdk, уже склонированные исходники и уже сконфигурированное дерево, а `make`
делает только недостающее.

## Что должно получиться

Три файла в `$BUILD_ROOT/artifacts` (именно три: README апстрима оговаривает,
что `soffice.wasm` собирается «попутно», а обязателен `soffice.data` — образ
in-memory ФС со шрифтами и ресурсами):

| Файл | Что это |
|---|---|
| `soffice.js` | загрузчик emscripten; в него вшиты pre-js апстрима (`static/emscripten/environment.js`, скрипты UNO-биндингов) |
| `soffice.wasm` | сам код LibreOffice |
| `soffice.data` | in-memory ФС: шрифты, `services.rdb`, ресурсы `cui/ui/*.ui` и прочее |

Рядом пишется `MANIFEST.txt`: пины, флаги, sha256 и размеры — по нему потом
заполняется `docs/sprint-13/build-log.md` и проверяется воспроизводимость.

**Куда девать.** Каталог `artifacts` целиком уходит в release asset GitHub
(внешнее хранилище); в git `*.wasm` и `soffice.data` не кладутся — это
десятки-сотни мегабайт несжатого бинаря. В репозиторий попадает только
`MANIFEST.txt`-сводка, переписанная в build-log, и вывод замеров.

## Когда что-то падает

| Признак | Что делать |
|---|---|
| Процесс убит на линковке (`Killed`, OOM killer), лог обрывается на `soffice_bin` | Уменьшить `JOBS` — компиляция вытесняет линковщик; затем `DISABLE_LTO=1`; в пределе — машина с большей RAM |
| `emscripten-finalize` ест часы и память | У LO в `gb_EMSCRIPTEN_LDFLAGS` уже стоят `WASM_BIGINT=1` и `ASSERTIONS=1` — перезапись гасится апстримом; проверить, что `EXTRA_LDFLAGS` не перебил их (`-g3` в них не добавлять) |
| `configure: error: no, found <версия>` на проверке Emscripten | Тулчейн ниже требуемого (≥ 3.1.46 на пинованном теге): поднять `EMSDK_VERSION` |
| Клон не совпал с пином («тег переставили?») | Снять актуальный sha (`git ls-remote --tags <url> <тег>`) и осознанно обновить `LO_COMMIT`/`EMSDK_COMMIT` |
| `make fetch` не может скачать tarball | Повторить: цель идемпотентна, уже скачанное не качается заново; при блокировке сети — зеркало через `--with-external-tar` |
| `Building LibreOffice as root is a very bad idea` | Работа идёт от root: LO отказывается собираться (кроме распознаваемого контейнера). Завести обычного пользователя и повторить от него — арендованные VM почти всегда дают root |
| `не найден soffice.data ни в одном из каталогов` | Сборка не дошла до линковки: смотреть хвост лога, искать первую ошибку выше |
| Файлы артефактов собраны из разных каталогов (предупреждение) | Часть файлов осталась от прошлого прогона: удалить `$BUILD_ROOT/artifacts` и `$BUILD_ROOT/core/instdir` и повторить |

Полный лог прогона — `$BUILD_ROOT/build-*.log`; при падении путь печатается в
последней строке вывода.

## Перед вторым прогоном

Скопируйте три файла из `artifacts` и `MANIFEST.txt` наружу (VM может быть
уничтожена), затем повторите прогон на **чистой** VM **с теми же** `BUILD_ROOT`
и `LO_SRC`: другие пути попадут в отладочную информацию и метаданные ФС, и
sha256 разойдётся там, где сборка на самом деле совпала. Процедура сверки —
в `docs/sprint-13/build-log.md`, раздел «Проверка воспроизводимости».
